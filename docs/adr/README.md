# アーキテクチャ決定記録（ADR）

このディレクトリは、後から「なぜこう決めたか」を追跡できるよう、設計判断をバージョン単位で記録します。読み手に応じて次の2種類に分けます。

- **プロダクトADR（企画者向け）:** ユーザーから見える動作（表側仕様）が変わるビジネス上の判断。意思決定者（上司・企画）がレビューする（例: カバー画像を1枚にするか複数枚にするか）。
- **技術ADR（開発者内部向け）:** エンジニアが意思決定する裏側の判断。表側の動作は変えないが、後続の保守に効く選択（例: ストレージ方式の選定・移行トリガー・ロールバック戦略）。

> V6 以降は、この2種類を `v{N}/product/`（プロダクト）と `v{N}/technical/`（技術）のフォルダに分けて配置します。V5 は分割前のため `v5/` 直下にプロダクトADRのみを置いています。

## 何をADRに残すか

- **プロダクトADRに残す:** ユーザーから見える動作・表示・できることが変わる判断（例: 合同主催者を公開ページに表示するか、オーナー退会時にイベントが残るか）。
- **技術ADRに残す:** 表側の動作は変えないが、後続の保守メンバーが再判断するために経緯を残したい裏側の判断（例: 保存先ストレージの選定・移行トリガー・ロールバック戦略）。
- **残す（決定の寿命）:** どちらも「今の規模・前提だから妥当」な判断については、**いつ見直すか（トリガー）と、後続が取りうる代替案の方向性**も残す。作成者が離任しても後続者が再判断できるようにするため。ただし選んだ案の具体的な実装手順は書かない。
- **残さない:** 具体的な実装手順（テーブル設計・クラス構成・マウントパス・設定値など）。これらは `docs/superpowers/plans/` の実装計画・`docs/superpowers/specs/` の設計に書きます。

## フォーマット（MADR ベース）

各ADRは次の構成で書きます。

1. 背景と課題
2. 決定ドライバー（判断基準）
3. 検討した選択肢
4. 各案のメリット・デメリット
5. 推奨と理由（Proposed 時のたたき台。決定は意思決定者に委ねる）
6. 決定（承認時に記入）
7. 影響・結果

**ステータス運用:** `Proposed`（提案・レビュー待ち）→ `Accepted`（採用）→ 必要なら `Superseded by ADR-XXXX`（後継に置換）。

**配置・命名:**

- V6 以降: `docs/adr/v{N}/{product|technical}/{4桁連番}-{slug}.md`。**技術ADRは、切り出し元となったプロダクトADRと同じ番号を付ける**（例: プロダクト `0004` の裏側判断 → 技術 `0004`）。1つのプロダクトADRから複数の技術ADRを分ける場合は枝番（`0004a` 等）で区別する。
- V5: `docs/adr/v5/{4桁連番}-{slug}.md`（分割前）
