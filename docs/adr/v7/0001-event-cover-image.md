# ADR-0001 イベントカバー画像の仕様

- **ステータス:** Accepted
- **日付:** 2026-06-21（提案） / 2026-06-27（採用）
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** 設計書 `docs/superpowers/specs/2026-06-21-event-cover-image-design.md`（承認後に作成）

## このADRで決めること

V7 で導入する「**イベントカバー画像**」について、ユーザーから見える仕様を決める。

具体的には次の判断を確定する。

- 画像をいくつ持てるか（1枚か複数か）
- 画像を必須にするか任意にするか／未設定時にどう見せるか
- ユーザーが何をアップロードできるか（対応形式・サイズ上限）
- 誰がアップロードできるか

> 裏側の作り（保存先ストレージ・配信方法・DBカラム・テスト方法など）は表側仕様ではないため、このADRには書かず実装計画（`docs/superpowers/plans/`）と設計（`docs/superpowers/specs/`）で定める。

## 背景と課題

現在、イベント一覧・詳細ページはテキスト情報のみで、視覚的な訴求力に乏しい。主催者がイベントの雰囲気やテーマを画像で伝えられず、参加者も一覧から興味を引くイベントを見つけにくい。

connpass 本家をはじめ一般的なイベントプラットフォームはイベントごとにカバー画像を持つ。本機能で主催者がイベントに画像を設定できるようにし、一覧・詳細ページの視認性と訴求力を高める。

## 判断の観点

| 観点 | 説明 |
|---|---|
| **訴求力** | 一覧・詳細でイベントの魅力が伝わるか |
| **主催者の手間** | 画像準備・設定の負担が過大でないか |
| **安全性** | 不正なファイルがアップロードされない仕組みか |
| **コスト** | 実装・保守・運用（ストレージ）の重さ |

## 土台（必須・採用）

**主催者がイベントに画像を設定でき、一覧・詳細ページで表示される。** これは V7 の最小要件であり議論の余地なく必須とする。論点は「何枚・必須か任意か・何をアップロードできるか・誰が設定できるか」に絞る。

## 決定事項ごとの選択肢評価

### ① 画像をいくつ持てるか

| 選択肢 | メリット | デメリット | 判断 |
|---|---|---|:---:|
| カバー画像1枚のみ | 実装・保守がシンプル。一覧/詳細の主目的を満たす。connpass 本家も同形式 | 複数の写真で雰囲気を伝えられない | **採用** |
| カバー画像 + 本文中に複数枚 | 説明が豊かになる | 本文のリッチエディタ対応が必要で実装が重い | 見送り（YAGNI） |
| 複数画像ギャラリー | 写真を多く見せられる | 中間テーブル・管理画面が複雑化 | 見送り（YAGNI） |

まずカバー画像1枚に絞る。一覧・詳細の視認性向上という目的はこれで満たせる。複数画像の必要性が実証されたら別バージョンで再検討する。

### ② 必須か任意か／未設定時の見せ方

| 選択肢 | メリット | デメリット | 判断 |
|---|---|---|:---:|
| 任意（未設定時はプレースホルダ表示） | 主催者の手間が小さい。画像がなくてもイベント作成できる | 画像なしイベントが混在し見た目が不揃い | **採用** |
| 必須 | 一覧の見た目が揃う | 画像準備が負担で作成のハードルが上がる | 見送り |

画像は任意とし、未設定のイベントには共通のプレースホルダ画像を表示する。作成のハードルを上げないことを優先する。

### ③ ユーザーが何をアップロードできるか

| 項目 | 決定 | 理由 |
|---|---|---|
| 対応形式 | JPEG / PNG / WebP | Web で一般的な画像形式。SVG はスクリプト混入リスクがあり除外 |
| サイズ上限 | 5MB | カバー画像として十分。サーバー負荷・ストレージを抑える |
| 寸法上限 | 4000×4000px | 極端に大きい画像を拒否しメモリ枯渇を防ぐ |

不正ファイル対策として、拡張子だけでなく実際の画像内容を検証する（標準検証）。サーバー側での画像再エンコードやウイルススキャンは運用コストに見合わないため今回は行わず、必要性が出たら別途検討する（「不要」ではなく「今はやらない」）。

### ④ 誰がアップロードできるか

| 選択肢 | メリット | デメリット | 判断 |
|---|---|---|:---:|
| 主催者・共同主催者 | 既存のイベント編集権限と一貫。共同運営でも画像を更新できる | — | **採用** |
| オーナーのみ | 権限が単純 | 共同主催者が他項目は編集できるのに画像だけ変更できず不揃い | 見送り |

画像の設定・変更は、既存のイベント編集権限を持つ人（オーナーと共同主催者）に許可する。

## 推奨（Proposed 時のたたき台）

- 画像は**カバー1枚・任意**とし、未設定時はプレースホルダを表示する
- アップロードできるのは **JPEG/PNG/WebP・5MB・4000×4000px まで**
- 設定できるのは**主催者・共同主催者**

いずれも「最小限で安全に始め、必要性が実証されたら拡張する」方針に沿う。

## 決定

推奨案（たたき台）をそのまま採用する。

確定した仕様:
- **画像枚数** → カバー画像1枚のみ。本文中の複数枚・ギャラリーは持たない。
- **必須/任意** → 任意。未設定のイベントには共通のプレースホルダ画像を表示する。
- **対応形式・上限** → JPEG / PNG / WebP、5MB まで、寸法 4000×4000px まで。拡張子だけでなく実コンテンツを検証する（標準検証）。再エンコード・ウイルススキャンは今回は行わない。
- **アップロード権限** → 主催者・共同主催者（既存のイベント編集権限と同じ）。

「最小限で安全に始め、必要性が実証されたら拡張する」方針で合意。ストレージの選定・配信方法などの裏側は、承認を受けて設計（`docs/superpowers/specs/`）・実装計画（`docs/superpowers/plans/`）で定める。

## この決定を見直すとき（ストレージ構成の移行トリガーと代替案）

> このセクションは「実装手順」ではなく、**後続の保守メンバーが現構成で運用できなくなったときに、いつ・なぜ見直し、どの方向の選択肢があるか**を判断するための材料を残すもの。具体的なマウントパス・接続情報・設定値などの実装詳細は設計（`docs/superpowers/specs/`）・実装計画（`docs/superpowers/plans/`）で定める。

### 現構成と、なぜそれを選んだか

カバー画像は、**サーバー（コンテナ）に永続ディスク（Volume）を1つ付け、そこに画像ファイルを置く**構成で運用している。配信先サービス（Railway）のコンテナは再起動・再デプロイのたびに中身がリセットされるため、永続ディスクを使わないと画像が消える。

この「永続ディスク方式」を選んだ理由:

- **最小コストで永続化できる。** 外部ストレージの契約・認証情報の管理が不要で、ローカル開発の保存方法とほぼ同じまま本番で永続化できる。
- **今の規模（サーバー1台運用）に十分。** 凝った構成を持ち込まず、必要になってから拡張する（YAGNI）。

### 現構成の限界

永続ディスクは**1台のサーバーに紐づく**ため、サービスを**複数台（複数インスタンス）に増やすと画像を共有できない**。増やした場合、片方で保存した画像がもう片方から見えず、「画像が出たり出なかったりする」不整合が起きる。したがって**この構成は単一インスタンス運用が前提**になる。

### 見直しトリガー（どれか1つでも該当したら再検討）

| トリガー | 具体的なシグナル | 何が問題になるか |
|---|---|---|
| **水平スケールの必要** | アクセス増でサーバーを複数台に増やしたい | 永続ディスクをインスタンス間で共有できず、画像表示が不整合になる |
| **高速配信（CDN）の必要** | 画像表示を世界各地で速くしたい／アプリ負荷を下げたい | アプリ経由・単一ノード配信では CDN を活かせない |
| **容量・コストの限界** | 画像が増え永続ディスクの容量・コストが見合わなくなる | ディスク増設より、従量課金のオブジェクトストレージが有利になりうる |
| **可用性・バックアップ要件** | 画像消失が許されない、世代バックアップが要る | 単一ディスク前提では冗長化・バックアップ運用の手当てが必要 |

### 取りうる代替案の方向性

現構成（永続ディスク）で困るのは主に「複数台にスケールしたいとき」。その場合は**全インスタンスから共有アクセスできるオブジェクトストレージ**へ移すのが基本方針になる。

| 方向性 | 概要 | 向いている状況 | トレードオフ |
|---|---|---|---|
| **現状維持（永続ディスク）** | 1台のサーバーに永続ディスクを付けて保存 | 単一インスタンスで十分な規模 | 複数台に増やせない・CDN に不向き |
| **Railway のオブジェクトストレージ** | 配信先サービス内の S3 互換ストレージ | Railway 内で完結させたい | 認証情報の設定が要る |
| **Cloudflare R2** | 外部の S3 互換ストレージ。転送量（エグレス）無料 | 配信量が多くコストを抑えたい | 外部サービスの契約・管理が増える |
| **AWS S3** | 実績豊富な定番の S3 互換ストレージ | AWS 中心の構成・周辺サービス連携 | 転送量課金・AWS アカウント管理 |

いずれの S3 互換案も、全インスタンスから同じ画像を参照できるため**水平スケールと両立**し、CDN 配信にも発展できる。まずは現構成（永続ディスク）で運用し、上記トリガーが顕在化してから、軽い順（Railway 内ストレージ → R2/S3）に検討する。先回りでの移行は YAGNI として避ける。

### 表側仕様への波及

オブジェクトストレージへ移行しても、**利用者から見える動作（画像をアップロードでき、一覧・詳細で表示される）は変わらない**ため、本 ADR の決定（①〜④）の改訂は不要。ただし保存先を切り替えられるようにする裏側の調整（保存先を設定で選べるようにする小改修）が必要で、これは設計・実装計画で扱う。

## 影響・結果

- イベント一覧・詳細ページにカバー画像が表示される。未設定イベントはプレースホルダ表示となる。
- イベント作成・編集フォームに画像アップロード欄が追加される。
- 画像の保存にストレージが必要になる（裏側の選定は実装計画で定める）。
- 将来、画像再エンコード・サムネイル生成・複数画像ギャラリーを検討する余地を残す。
