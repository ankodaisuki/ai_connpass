# ADR-0003 招待の承認フロー

- **ステータス:** Accepted
- **日付:** 2026-06-08
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** [ADR-0001 方式選定](0001-joint-organizer-method.md) / [ADR-0002 権限モデル](0002-co-organizer-permission-model.md)

## このADRで決めること

招待された人が**どうやって合同主催者になるか**（本人の同意が必要か）。あわせて**合同主催者を公開ページに表示するか**（論点4）を決める。

## 背景と課題

合同主催者を追加するとき、招待された本人の同意なしに即座に主催者にしてよいか。本アプリではイベント詳細ページに主催者情報が出るため、**同意なく公開ページに名前が出る**懸念がある。招待の手軽さと、押し付け防止のバランスを決める。

## 決定ドライバー

| # | 判断基準 | 説明 |
|---|---|---|
| D1 | 本人同意 | 勝手に主催者にされない・公開されないことを担保できるか |
| D2 | 手軽さ | 招待してすぐ共催を始められるか |
| D3 | 実装コスト | 状態管理・通知の作り込み量 |
| D4 | 通知基盤の再利用 | 既存のメール送信基盤を活かせるか |

## 検討した選択肢

- **案A: 即時追加** — 招待した時点で相手は合同主催者になる。承認は不要。
- **案B: 承認制** — 招待を送ると相手は「保留中」。相手が承諾して初めて合同主催者になる。辞退もできる。
- **案C: 承認制＋期限・リマインド** — 案Bに、招待の有効期限・自動失効・リマインド通知を加える。

## 各案のメリット・デメリット

評価記号: ◎=強い / ○=可 / △=弱い / ▲=コスト高

| 観点 | 案A 即時 | 案B 承認制 | 案C 承認制+期限 |
|---|:---:|:---:|:---:|
| D1 本人同意 | △ なし | ◎ | ◎ |
| D2 手軽さ | ◎ | ○ | ○ |
| D3 実装コスト | ◎ 軽い | ○ | ▲ 重い |
| D4 通知基盤の再利用 | － | ◎ | ◎ |

**案A 即時追加**

- ＋ 実装が軽く、招待してすぐ共催を始められる（D2, D3）。
- ＋ 信頼関係のある相手なら手間がない。
- − 同意なく主催者にされ、自分のプロフィールや公開ページに知らないイベントが共催として出る恐れ（D1）。

**案B 承認制**

- ＋ 本人同意を担保。勝手に巻き込まれない（D1）。
- ＋ 「招待中／承諾済み」の状態が明確で、UX がはっきりする。
- ＋ 通知は既存のメール基盤（`EventCancelledMail` 等と同じ仕組み）を再利用できる（D4）。
- − 承諾されるまで主催者が増えない。イベント直前の招待では即時性に欠ける（D2）。
- − 保留／承諾／辞退の状態管理が必要（D3）。

**案C 承認制＋期限・リマインド**

- ＋ 最も丁寧。期限切れ自動失効やリマインドで招待の放置を防げる。
- − V5 には過剰。スケジューラやリマインド通知の作り込みで実装が重い（D3）。

## 推奨と理由（たたき台）

**案B 承認制を推奨。**

- 「勝手に主催者にされない・公開されない」は表側仕様として重要（D1）。特に公開ページに名前が出る本アプリでは同意取得が望ましい。
- 通知は既存メール基盤を再利用でき、実装コストは中程度に収まる（D3, D4）。
- 期限・リマインド（案C）は将来拡張として切り出す。

### 合同主催者の公開表示（論点4）

- **承諾済み（accepted）の合同主催者のみ**をイベント詳細（公開ページ）に表示する。
- **保留中（pending）／辞退（declined）は公開ページに出さない。**
- これにより「同意した人だけが公開される」となり、案Bの承認制と整合する。これは表側仕様。

### フローのイメージ（案Bの場合）

```
オーナーが招待
   │
   ▼
[ pending（保留中） ]  ← 公開ページには出ない / 被招待者にメール通知
   │            │
 承諾            辞退
   ▼            ▼
[ accepted ]   [ declined ]
合同主催者として  主催者にならない
公開ページに表示
```

## 決定

**案B・承認制を採用。公開ページには承諾済み（Accepted）のみ表示する。**

- 同意なく公開ページに名前が出ることを防ぐため、承認制を採用（D1）。
- 招待は既存のメール基盤を再利用し、実装コストを中程度に抑える（D3, D4）。
- 期限・リマインド（案C）は V6 以降の拡張とする。
- 招待状態は `pending`（保留）/ `accepted`（承諾）/ `declined`（辞退）の3値で管理する。

## 影響・結果

- **採用＝案B（推奨）の場合の表側仕様:**
  - 招待された人は、承諾するまで合同主催者にならない。辞退もできる。
  - 公開ページには承諾済みの合同主催者のみ表示される。
- **実装方針の参考（裏側・詳細は実装計画にて）:** 中間テーブルに招待状態（pending / accepted / declined）の列を持たせ、招待時に被招待者へメール通知を送る想定。
