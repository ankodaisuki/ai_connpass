# ADR-0002 合同主催者の権限モデル

- **ステータス:** Proposed（提案中・レビュー待ち）
- **日付:** 2026-06-08
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** [ADR-0001 方式選定](0001-joint-organizer-method.md) / [ADR-0003 招待の承認フロー](0003-invitation-approval-flow.md)

## このADRで決めること

合同主催者に**どこまでの操作を許すか**。オーナー（作成者）との権限差をどうつけるか。あわせて**オーナーが離脱したときの扱い**（論点5）を決める。

## 背景と課題

現状 `EventPolicy` は、編集・削除・出欠記録のすべてを「作成者本人のみ」に許可している。合同主催者が増えると、誰がどの操作をできるかを定義し直す必要がある。

特に本アプリのイベントには**参加者が紐づく**（申込・キャンセル待ち・出欠記録）。誤ってイベントを削除すると参加者へ中止通知が飛ぶなど影響が大きいため、強い権限（削除・主催者の追加削除）を誰に許すかは慎重な判断を要する。

## 決定ドライバー

| # | 判断基準 | 説明 |
|---|---|---|
| D1 | 誤操作リスク | 特にイベント削除・主催者除名の事故をどれだけ防げるか |
| D2 | 責任の所在 | 最終責任者（オーナー）が明確か |
| D3 | 運用の柔軟性 | 役割分担（受付だけ任せる等）に対応できるか |
| D4 | 実装・UIの単純さ | ロール概念の有無による複雑さ |

## 検討した選択肢

- **案A: フラット** — オーナーと合同主催者を区別せず、全員が全権限（編集・削除・出欠記録・主催者の招待/除名）を持つ。
- **案B: 2階層** — `owner`（作成者）と `co_organizer`（合同主催者）の2ロール。合同主催者は編集・出欠記録・参加者閲覧は可能だが、**イベント削除と主催者の招待/除名はオーナーのみ**。
- **案C: 複数ロール** — `owner` / `editor`（編集可）/ `receptionist`（出欠受付のみ）など、操作単位でロールを細分化する。

## 各案のメリット・デメリット

評価記号: ◎=強い / ○=可 / △=弱い / ▲=コスト高

| 観点 | 案A フラット | 案B 2階層 | 案C 複数ロール |
|---|:---:|:---:|:---:|
| D1 誤操作リスク | ▲ 誰でも削除可 | ◎ | ◎ |
| D2 責任の所在 | △ 不明確 | ◎ 明確 | ◎ |
| D3 運用の柔軟性 | △ | ○ | ◎ |
| D4 実装・UIの単純さ | ◎ 最小 | ◎ ロール2種 | ▲ 複雑 |

**操作ごとの権限イメージ（案Bの場合）**

| 操作 | owner | co_organizer |
|---|:---:|:---:|
| イベント閲覧 | ✓ | ✓ |
| イベント編集 | ✓ | ✓ |
| 出欠記録 | ✓ | ✓ |
| 参加者一覧の閲覧 | ✓ | ✓ |
| イベント削除 | ✓ | ✗ |
| 合同主催者の招待 / 除名 | ✓ | ✗ |
| オーナー権限の移譲 | ✓ | ✗ |

**案A フラット**

- ＋ 実装が最小。ロール概念が不要で UI もシンプル。
- ＋ 完全に対等。強い信頼関係のある小規模共催に向く。
- − 誰でもイベント削除・主催者除名ができ、誤操作や関係悪化時の事故リスクが大きい（D1）。
- − 最終責任者が不明確（D2）。

**案B 2階層**

- ＋ 誤削除・乗っ取りを防げる。最終責任者（オーナー）が明確（D1, D2）。
- ＋ ロールは2種だけなので UI・実装ともに単純（D4）。
- ＋ 多くのユースケースに十分。
- − 「合同主催者にも削除させたい」要望には直接応えられない（ただしオーナー権限の移譲で対応可能）。

**案C 複数ロール**

- ＋ 最も柔軟。「受付だけ任せる」等の細かい分担ができる（D3）。
- ＋ 大規模運営に向く。
- − 設計・UI・テストが複雑になり、V5 には過剰（D4）。
- − ロール設計を誤ると後の変更コストが高い。

## 推奨と理由（たたき台）

**案B 2階層（`owner` / `co_organizer`）を推奨。**

- 参加者が紐づくイベントの誤削除・乗っ取りリスクを抑えられる（D1）。削除と主催者管理をオーナー限定にするのが安全。
- ロールが2種なので UI もシンプルに保てる（D4）。
- 将来 案C（複数ロール）が必要になっても、ロール列の値を増やす拡張で対応できる（具体的な実装は裏側の話なので実装計画にて）。

### オーナー離脱・権限移譲（論点5＝「予定が消える/消えない」）

- **オーナーがイベントを削除した場合:** 従来どおり削除可能（オーナーの権限）。参加者がいる場合は既存の中止通知メールが飛ぶ。
- **オーナーが退会（アカウント削除）した場合:** **イベントは削除せず残す。** オーナー権限は、残っている合同主催者のうち最も早く参加した者へ自動的に移譲する。
  - これが論点5でいう **「予定が消えない」** の選択。参加者保護のため、主催者が1人抜けてもイベントと申込は維持する、という表側仕様。
- **合同主催者が1人も残っていない状態でオーナーが退会した場合:** イベントを「主催者不在」とせず、**下書き（非公開）に戻して新規申込を止める**ことを推奨（既存の参加者・申込データは保持）。この具体挙動はレビューで決める論点。
- **手動の権限移譲:** オーナーが任意で合同主催者の1人に `owner` を譲れる機能。**V5 に含めるかは任意**（自動移譲だけで最小要件は満たせるため）。レビューで要否を判断する。

## 影響・結果

- **採用＝案B（推奨）の場合の表側仕様:**
  - 合同主催者はイベントを削除できず、他の主催者を招待・除名できない。
  - オーナーが退会してもイベントは残り、権限が他の主催者へ移る。
- **実装方針の参考（裏側・詳細は実装計画にて）:** `EventPolicy` を拡張し、`update` / `updateAttendance` はオーナー＋合同主催者に許可、`delete` と主催者管理はオーナーのみに許可する想定。ロールは中間テーブルの列で保持。
