# ADR-0002 合同主催者の権限モデル

- **ステータス:** Proposed（提案中・レビュー待ち）
- **日付:** 2026-06-08（初版）／ 2026-06-13（画面目線へ改訂・主催者不在時の挙動を明確化）
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** [ADR-0001 方式選定](0001-joint-organizer-method.md) / [ADR-0003 招待の承認フロー](0003-invitation-approval-flow.md)

## このADRで決めること

合同主催者が、イベントの画面で**どこまで操作できるか**。オーナー（作成者）との違いをどうするか。あわせて、**オーナーがいなくなったときイベントや参加者の予定がどうなるか**（論点5）を決める。

## 背景と課題

いまは、イベントを作成した本人（オーナー）だけが、次の操作を行えます。

- イベントの編集
- イベントの削除
- 出欠の記録（参加者の出席チェック）
- 参加者一覧の閲覧

合同主催者が増えると、「**合同主催者の画面にどのボタンを出すか＝何を許すか**」を決め直す必要があります。

特に本サービスのイベントには参加者が紐づきます。誤ってイベントを削除すると参加者へ中止メールが飛ぶなど影響が大きいため、「削除」や「他の主催者を外す」といった強い操作を誰に許すかは慎重に決めます。

## 決定ドライバー

| # | 判断基準 | 説明 |
|---|---|---|
| D1 | 誤操作・事故の防ぎやすさ | 参加者がいるイベントの誤削除・主催者の誤除名をどれだけ防げるか |
| D2 | 責任の所在 | 最終責任者（オーナー）が誰か明確か |
| D3 | 運用の柔軟性 | 「受付だけ任せる」等の役割分担に対応できるか |
| D4 | 画面・操作のわかりやすさ | 利用者にとって画面がシンプルか |

## 検討した選択肢

- **案A フラット** — オーナーと合同主催者を区別しない。合同主催者の画面にもすべての操作ボタン（編集・削除・主催者の招待/除名）が出る。
- **案B 2階層** — オーナーと合同主催者を分ける。合同主催者は編集・出欠記録・参加者閲覧はできるが、削除と主催者の招待/除名のボタンは出ない（オーナーだけ）。
- **案C 複数ロール** — 「編集担当」「受付担当」など役割を細かく分け、役割ごとに見えるボタンが変わる。

## 画面イメージ（合同主催者から見たイベント管理画面）

```
■ 案A フラット
  イベント管理: Laravel勉強会 #5
  ┌────────────────────────────────────────┐
  │ [イベントを編集] [出欠を記録] [参加者一覧]  │
  │ [合同主催者を招待] [イベントを削除]         │
  └────────────────────────────────────────┘
  → 合同主催者にも「すべて」の操作ボタンが出る


■ 案B 2階層
  イベント管理: Laravel勉強会 #5
  ┌────────────────────────────────────────┐
  │ [イベントを編集] [出欠を記録] [参加者一覧]  │
  └────────────────────────────────────────┘
  → 「イベントを削除」「合同主催者を招待/除名」は出ない
     （これらはオーナーの画面にだけ表示される）


■ 案C 複数ロール
  ＜編集担当の画面＞              ＜受付担当の画面＞
  ┌──────────────────┐        ┌──────────────────┐
  │ [イベントを編集]    │        │ [出欠を記録]       │
  │ [参加者一覧]        │        │ [参加者一覧]       │
  └──────────────────┘        └──────────────────┘
  → 役割ごとに見えるボタンが変わる（設定がきめ細かい）
```

## できること比較（案Bの場合の例）

| 画面でできること | オーナー | 合同主催者 |
|---|:---:|:---:|
| イベントを編集 | ✓ | ✓ |
| 出欠を記録 | ✓ | ✓ |
| 参加者一覧を見る | ✓ | ✓ |
| イベントを削除 | ✓ | ✗ |
| 合同主催者を招待 / 除名 | ✓ | ✗ |
| オーナーを引き継ぐ | ✓ | ✗ |

**案A フラット**

- ＋ 全員が同じ画面で分かりやすく、すぐ使える。
- ＋ 強い信頼関係のある小規模な共催に向く。
- − 合同主催者の画面にも削除ボタンが出るため、誤って消す・主催者を外す事故が起きうる（D1）。
- − 画面から最終責任者が誰か分からない（D2）。

**案B 2階層**

- ＋ 合同主催者の画面に削除等が出ないので、誤削除・乗っ取りを防げる（D1）。
- ＋ オーナーが誰か明確（D2）。役割は2種だけで画面もシンプル（D4）。
- ＋ 多くの使い方に十分。
- − 「合同主催者にも削除させたい」場合は、オーナーを引き継いでもらう必要がある。

**案C 複数ロール**

- ＋ 「受付だけ任せる」等の細かい分担ができる（D3）。
- − 役割を設定する画面が増え、利用者には分かりにくい（D4）。V5 には過剰。

## 推奨と理由（たたき台）

**案B 2階層を推奨。**

- 参加者がいるイベントの誤削除・乗っ取りを、画面にボタンを出さないことで未然に防げる（D1）。
- オーナーが誰か明確で（D2）、画面も2役割だけでシンプル（D4）。
- 将来もっと細かい役割分担が必要になれば、段階的に役割を増やして対応できる。

### オーナー離脱・権限移譲（論点5＝「予定が消える/消えない」）

合同主催者が増えると「主催者の誰かが抜けたとき、参加者の予定をどう扱うか」を決める必要があります。基本方針は **「黙っては消さない」**。

- **オーナーがイベントを削除したとき:** 従来どおり削除。参加者がいれば中止メールが飛ぶ。
- **オーナーが退会したとき（合同主催者が残っている）:** イベントは消さず、**合同主催者のうち最初に参加した人がオーナーを引き継ぐ。** 参加者の画面では予定がそのまま見える。
- **オーナーが退会したとき（合同主催者もいない）:** イベントを**中止扱い**にし、参加者に中止メールを送る（既存の中止通知の仕組みを流用）。参加者の申込一覧には**「中止」と分かる形で残り、黙って消えることはない。**
- **手動の引き継ぎ:** オーナーが任意で合同主催者の1人にオーナーを譲る機能。**V5 に入れるかは任意**（自動の引き継ぎだけでも最小要件は満たせる）。※要決定。

```
■ オーナーが退会したとき、参加者の「申し込んだイベント」画面

   ✕ 採らない案：黙って予定を消す
     ┌──────────────────────────┐
     │ （表示なし）                │  ← 理由も分からず予定が消滅
     └──────────────────────────┘

   ◎ 推奨案：黙っては消さない
     ① 合同主催者が残っている → そのまま表示（自動で引き継ぎ）
     ┌──────────────────────────┐
     │ Laravel勉強会 #5   6/20 19:00〜 │
     └──────────────────────────┘
     ② 合同主催者もいない → 「中止」と明示（中止メールも届く）
     ┌──────────────────────────┐
     │ Laravel勉強会 #5   ⚠ 中止されました │
     └──────────────────────────┘
```

> 論点5「予定が消える/消えない」は、**参加者の画面から予定が消えるかどうか**という表側の違い。推奨は **「黙っては消さない」**——合同主催者が残れば予定は維持し、誰も残っていなければ中止と明示して通知する。

## 影響・結果

- **採用＝案B（推奨）の場合、ユーザーから見える動き:**
  - 合同主催者の画面には「イベントを削除」「合同主催者を招待/除名」のボタンが出ない。
  - オーナーが退会しても、合同主催者が残っていれば予定は維持される。誰も残っていない場合はイベントを中止扱いにして参加者へ通知する（黙って消さない）。
- 具体的な実装方法（権限チェックの作り方など）は、**採用が決まってから実装計画（`docs/superpowers/plans/`）で定める。**
