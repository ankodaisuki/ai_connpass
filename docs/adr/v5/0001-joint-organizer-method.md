# ADR-0001 合同主催の方式選定

- **ステータス:** Proposed（提案中・レビュー待ち）
- **日付:** 2026-06-08
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** [ADR-0002 権限モデル](0002-co-organizer-permission-model.md) / [ADR-0003 招待の承認フロー](0003-invitation-approval-flow.md)

## このADRで決めること

複数人で1つのイベントを主催する「合同主催」を、**どの方式で実現するか**。

## 背景と課題

現状、イベントの主催者は作成者1人だけ（`events.user_id` による単一オーナー）。`EventPolicy` でも編集・削除・出欠記録はすべて「作成者本人のみ」に制限されている。

複数人で1つのイベントを主催したいニーズがあり、想定シーンは幅広い。

- **単発の共催** — 今回だけ知人や別の人と共同開催。次回は相手が変わる。
- **固定チームの運営** — コミュニティ／運営スタッフのほぼ同じ顔ぶれで繰り返し開催。
- **複数コミュニティの合同開催** — 別々の主催者同士が1イベントを共同主催。

この幅広いシーンを、どのUI／概念モデルで提供するかを決める。

## 決定ドライバー

| # | 判断基準 | 説明 |
|---|---|---|
| D1 | シーン網羅性 | 単発共催〜固定チーム運営まで対応できるか |
| D2 | 実装コスト | 初回リリースまでの開発量 |
| D3 | 段階導入のしやすさ | 小さく出して価値検証できるか |
| D4 | UX | 招待の手間、繰り返し開催の効率 |
| D5 | 拡張性・保守性 | 将来のロール追加・グループ化に耐えるか |
| D6 | connpassらしさ | 本家 connpass はコミュニティ（グループ）が主軸 |

## 検討した選択肢

- **案A: 個別ユーザー招待のみ** — イベント単位で、主催者が別ユーザーを1人ずつ合同主催者として招待する。
- **案B: グループ機能のみ** — グループ（コミュニティ）を作成してメンバーを管理し、イベントにグループを紐付けることでメンバーが合同主催者になる。
- **案C: 両方（段階導入）** — まず案A（個別招待）を提供し、後からグループ機能を追加する。

## 各案のメリット・デメリット

評価記号: ◎=強い / ○=可 / △=弱い / ▲=コスト高

| 観点 | 案A 個別招待 | 案B グループ | 案C 両方(段階) |
|---|:---:|:---:|:---:|
| D1 単発共催 | ◎ | △ | ◎ |
| D1 固定チーム運営 | △ | ◎ | ◎ |
| D2 実装コスト | ◎ 軽い | ▲ 重い | ▲ 最大 |
| D3 段階導入 | ◎ | △ | ◎ |
| D4 繰り返し開催の効率 | △ 毎回招待 | ◎ 使い回せる | ◎ |
| D5 拡張性 | ○ | ◎ | ◎ |
| D6 connpassらしさ | △ | ◎ | ◎ |

**案A 個別招待のみ**

- ＋ 実装が最も軽い。中間テーブルと招待機能だけで成立する。
- ＋ 単発の共催に最適。相手が毎回変わっても柔軟。
- ＋ 小さくリリースして価値検証できる。
- − 固定メンバーで繰り返すと、毎回同じ人を1人ずつ招待する手間が発生。
- − 「コミュニティ／団体」という概念がないため、団体としての主催表現が弱い。

**案B グループのみ**

- ＋ 固定チーム運営に最適。一度グループを作れば以後のイベントで使い回せる。
- ＋ 本家 connpass に近い（connpass はコミュニティが主軸）。団体としての主催表現ができる。
- − 実装が重い（グループのCRUD、メンバー管理、グループ↔イベント連携、権限）。
- − 単発の共催には過剰。グループを作るほどでない相手と1回だけ共催、が面倒。
- − グループに属さない個人を1人だけ招待、ができず柔軟性に欠ける。

**案C 両方（段階導入）**

- ＋ 幅広いシーンを全部カバー（単発は招待、固定はグループ）。
- ＋ 段階導入でリスク分散。まず招待で価値を検証し、その後グループを追加できる。
- ＋ グループ招待を「グループメンバーを個別招待の仕組みへ展開する」形にすれば、案Aの基盤を再利用できる。
- − 総実装コストが最大。2つの主催ルートが併存し、権限・公開表示の整合を取る必要がある。
- − 将来グループを足す前提でデータモデルを設計しないと、後から手戻りが生じる。

## 推奨と理由（たたき台）

**案C・段階導入を推奨。ただし V5 の実装範囲は案A（個別招待）に限定する。**

- 「幅広いシーンに対応したい」という方針から、最終形は案C（両方）が望ましい（D1）。
- 一方で案Bを最初から作ると実装コストが大きく（D2）、リリースが遅れる。まず案Aで価値を検証するのが堅実（D3）。
- データモデルだけは将来のグループ導入を見越して設計し、グループ追加時に個別招待の基盤を再利用できるようにする（D5）。

### 表側仕様への影響（重要）

> **V5 時点でユーザーから見えるのは「個別ユーザーの招待」だけ。** グループの作成・グループ単位の主催は V5 では提供しない（V6 以降）。
>
> これは「ユーザーから見える動作」が変わる判断のため、本ADRで明示的に残す。グループを V5 に含めるか否かは、レビューで覆しうる論点。

## 決定

未決定（本ADRは Proposed）。レビューで採用案（A / B / C）と V5 の実装範囲を確定し、本欄に理由とともに記入する。採用後は ステータスを Accepted に更新する。

## 影響・結果

- **採用＝案C段階導入（推奨）の場合の表側仕様:** V5 では個別招待で合同主催者を追加できる。グループUIは存在しない。
- **移行:** 既存イベントの作成者（`user_id`）は「オーナー」として扱う（権限の詳細は [ADR-0002](0002-co-organizer-permission-model.md)）。
- **実装方針の参考（裏側・詳細は実装計画にて）:** 主催者の多対多は中間テーブル＋ロール列で表現し、将来グループから展開された主催者も同じ表に載せられる形を想定。具体的なテーブル設計はADRの決定事項ではなく `docs/superpowers/plans/` に記載する。
