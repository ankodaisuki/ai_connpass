# ADR-0002 不適切対処（運営者によるイベント削除・ユーザー凍結）の仕様

- **ステータス:** Accepted
- **日付:** 2026-06-17（提案）
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** 要件書 UC7（不適切なイベント・ユーザーへの対処・運営者視点）

## このADRで決めること

V6 で導入する「**運営者（プラットフォーム運営）**」が、不適切なイベント・ユーザーへどう対処できるかの**画面上の振る舞い**を決める。

具体的には、運営者ができる操作（イベント削除・ユーザー凍結）を前提に、次の判断を確定する。

- 対処の起点（利用者からの通報を受けるか、運営者が自分で見つけるか）
- 凍結したとき、そのユーザーの周りに何が起きるか
- イベントを削除したとき、参加者に何が起きるか
- 「なぜ対処したか（理由）」を誰が見られるか
- 運営者という役割をどれだけ作り込むか

> 裏側の作り（凍結状態の持ち方・テーブル構成・ログイン遮断の仕組み・既存削除処理の流用など）は表側仕様ではないため、このADRには書かず実装計画（`docs/superpowers/plans/`）で定める。

## 背景と課題

誰でも無料でイベントを立てられる本サービスでは、スパムイベントや規約違反の投稿、迷惑行為を繰り返すユーザーが現れうる。現状、運営側がこれらに対処する手段が一切ない。

そこで「**プラットフォーム運営をするアカウント（運営者）**」を設け、不適切なイベントの削除と、迷惑ユーザーの利用停止（凍結）をできるようにする。

不適切対処は後からトラブル（「なぜ消されたのか」「誰が決めたのか」）になりやすい領域のため、**透明性（理由の提示）**と**追跡可能性（操作の記録）**を判断の軸に含める。

## 判断の観点

| 観点 | 説明 |
|---|---|
| **対処の確実性** | 不適切なものを運営者が確実に止められるか |
| **巻き添えの小ささ** | 対処が、無関係な参加者・共催者に予期せぬ影響を与えないか |
| **透明性 / 説明責任** | 対処された本人が理由を分かり、運営側も後から追跡できるか |
| **コスト** | 実装・保守の重さ（画面・ロジック・既存機能との整合） |

## 土台（必須・採用）

**運営者がイベントを削除でき、ユーザーを凍結（利用停止）できる。** これは UC7 の最小要件であり議論の余地なく必須とする。論点は「その振る舞いをどう確定するか」に絞る。

## 決定事項ごとの選択肢評価

### ① 対処の起点 — 通報を受けるか / 運営者が見つけるか

| 選択肢 | 価値 | コスト | 判断 |
|---|---|---|:---:|
| 運営者の対処のみ（通報なし） | まず運営者が見つけて消す・止める最小機能を満たす | 小 | **採用** |
| 利用者からの通報も受ける | 不適切の発見が早くなる | 通報画面・通報一覧・重複/濫用対策が増える | **見送り**（YAGNI） |

通報機能は便利だが、まず運営者が対処できる土台を作り、必要性が出てから足す。

### ② 凍結したときの周り — アカウントのみ止めるか / 連鎖させるか

| 選択肢 | 巻き添えの小ささ | コスト | 判断 |
|---|:---:|---|:---:|
| アカウントのみ凍結 | 大（周りに影響しない） | 小 | **採用** |
| 凍結と同時にそのユーザーのイベントも一括で非公開化 | 小（連鎖が広がる） | 連鎖の復元・参加者影響・合同主催イベントの扱いが複雑化 | **見送り** |

**凍結＝そのユーザーのログインを止めるだけ**とする。イベントが問題なら別途「イベント削除」で個別に消す。凍結と削除を独立した道具に保つことで、巻き添えと復元の複雑さを避ける。

これに伴い、凍結の付随仕様を次のとおり定める。

- **参加者への通知 → しない。** 凍結してもイベントは継続するため、参加者から見て何も変わらない。「主催者が凍結された」と通知すると、開催されるイベントなのに参加者が不安になるだけ。イベント自体が問題なら削除（③）で扱う。
- **合同主催イベントでの自動昇格 → しない。** 凍結されたユーザーがオーナーでも、承諾済みの合同主催者は従来どおり編集・出欠記録・リマインド送信を続けられる（V5 の権限）。凍結を「純粋なアカウント停止」に留め、オーナー譲渡は従来どおり手動とする。凍結が V5 の承認制譲渡を裏口で上書きするのを避ける。

```
■ あるユーザーを凍結したとき
  本人        → ログインできなくなる（理由が画面に表示される）
  そのイベント → そのまま継続（参加者は申込のまま・通知なし）
  合同主催者   → これまでどおりイベントを運営できる（昇格は起きない）
```

### ③ イベントを削除したときの参加者 — 通知するか / しないか

| 選択肢 | 透明性 | コスト | 判断 |
|---|:---:|---|:---:|
| 申込済みの参加者へ通知する | 高（予定が消えた理由が分かる） | 小（既存の中止通知の仕組みを流用） | **採用** |
| 通知しない | 低（イベントが突然消えて理由不明） | 最小 | **見送り** |

参加予定だったイベントが消えるため、申込済み参加者へ「**運営により削除された**」旨と理由（④）をメールで通知する。削除はやり直しが効く（運営側で復元可能）形とする。

### ④ 理由の扱い — 本人に伝えるか / 内部のみか / 記録しないか

| 選択肢 | 透明性 / 説明責任 | 判断 |
|---|:---:|:---:|
| 理由を入力必須にし、本人にも伝える | 高 | **採用** |
| 理由は入力必須だが内部記録のみ | 中 | 見送り |
| 理由を記録しない | 低 | 見送り |

運営者は凍結・削除のたびに**理由を必ず入力**する。凍結された本人はログイン拒否画面で理由を見られ、削除イベントの参加者には通知メールに理由が含まれる。透明性を確保し、苦情対応をしやすくする。

### ⑤ 操作の記録（監査ログ） — 残すか / 残さないか

| 選択肢 | 追跡可能性 | コスト | 判断 |
|---|:---:|---|:---:|
| 誰が・いつ・何を・なぜ を記録し、運営画面で見られる | 高 | 中 | **採用** |
| 記録しない | 低 | 小 | 見送り |

凍結・解除・イベント削除の履歴を運営画面で確認できるようにする。複数運営者での運用・事後検証・説明責任に備える。

### ⑥ 運営者という役割の作り込み

| 選択肢 | コスト | 判断 |
|---|---|:---:|
| 単一の役割。運営者は内部手続き（運用作業）でのみ任命 | 小 | **採用** |
| 運営者が画面から他のユーザーを運営者に任命できる | 中（権限乗っ取りリスク・任命管理画面） | 見送り |
| 複数階層（モデレーター / 管理者など） | 大 | 見送り（YAGNI） |

運営者は1種類のみとし、画面からの昇格は設けない。最小で安全な構成にとどめ、必要性が出てから段階的に拡張する。

## 運営画面のイメージ（参考）

```
/admin/users       ユーザー一覧（検索）   [凍結] / [解除]  ← 理由入力
/admin/events      イベント一覧          [削除]           ← 理由入力
/admin/audit-logs  操作履歴（誰が・いつ・何を・なぜ）

 ── ユーザー管理 ──────────────────────────────
 検索: [ 名前 / メール          ]  [検索]
 山田太郎  taro@example.com   有効    [凍結]
 佐藤花子  hana@example.com   凍結中  [解除]   理由: スパム投稿
 ────────────────────────────────────────────
```

一般の利用者には運営画面・運営操作は一切表示されない。

## 推奨と理由（たたき台）

**運営者の対処のみ（通報なし）で土台を作り、凍結はアカウントのみ・通知なし・自動昇格なし、イベント削除は参加者へ通知（運営削除＋理由）、理由は本人に提示、操作は監査ログに記録、運営者は単一役割。**

- 土台だけで UC7 の目的（運営者が不適切なイベント・ユーザーへ対処する）を満たせる。
- 凍結と削除を独立させ、巻き添えと復元の複雑さを避ける。
- 理由の提示と操作記録で、後のトラブルに対する透明性・説明責任を確保する。
- 通報・画面任命・複数階層は便利だが今はコストに見合わないため見送る（YAGNI）。

## 決定

推奨案をそのまま採用する。

確定した仕様:
- 対処の起点 → **運営者の対処のみ。通報機能は設けない。**
- 凍結の範囲 → **アカウントのみ凍結（ログイン停止）。参加者通知なし・合同主催者の自動昇格なし。**
- イベント削除 → **申込済み参加者へ「運営により削除」＋理由を通知。運営側で復元可能。**
- 理由 → **入力必須。本人（凍結ユーザー・削除イベントの参加者）に提示する。**
- 操作記録 → **凍結・解除・削除を監査ログに記録し、運営画面で確認できる。**
- 運営者 → **単一の役割。画面からの任命は不可（内部手続きで任命）。**

## 影響・結果

- **ユーザーから見える動き:**
  - 運営者は専用の運営画面でユーザーを凍結／解除し、不適切なイベントを削除できる。
  - 凍結されたユーザーはログインできなくなり、画面で凍結理由を確認できる。本人のイベント・申込・合同主催はそのまま残る。
  - 運営者にイベントを削除された場合、申込済みの参加者へ「運営により削除された」旨と理由がメールで届く。
  - 一般の利用者には運営画面・運営操作は一切見えない。
- 見送った候補（通報・画面任命・複数階層）は、必要性が実証されたら別バージョンで再検討する。通報は将来の発見性向上策として、運営対処の土台ができた後に検討する。
- 具体的な実装方法（凍結状態の持ち方・退会処理との切り分け・ログイン遮断の仕組み・既存中止通知の流用・監査ログのテーブル設計）は、採用が決まってから実装計画（`docs/superpowers/plans/`）で定める。
