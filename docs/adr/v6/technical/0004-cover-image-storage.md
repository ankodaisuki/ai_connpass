# ADR-0004（技術）カバー画像の保存先ストレージ方式

- **種別:** 技術ADR（開発者内部向け・裏側の実装判断）
- **ステータス:** Accepted（保存先ストレージ） / 一部 Proposed（末尾「アップロード画像のウィルス・不正ファイル対策」は提案・未決定）
- **日付:** 2026-06-27（当初方式の採用） / 2026-06-29（Cloudflare R2 へ移行） / 2026-07-05（ウィルス対策の方式比較を追記）
- **決定者:** 開発チーム
- **関連:** プロダクトADR `../product/0004-event-cover-image.md`（表側仕様） / 設計書 `docs/superpowers/specs/2026-06-28-cover-image-r2-migration-design.md` ／ 実装計画 `docs/superpowers/plans/2026-06-28-cover-image-r2-migration.md`

## このADRで決めること

プロダクトADR `../product/0004-event-cover-image.md` で確定した「イベントカバー画像」機能の**裏側 = 画像ファイルの保存先ストレージ方式**を決める。あわせて、**現構成をいつ・なぜ見直すか（移行トリガー）と、取りうる代替案の方向性**、および**実際に行った移行の記録**を残す。

> このADRは「実装手順」そのものではなく、**後続の保守メンバーが現構成で運用できなくなったときに、いつ・なぜ見直し、どの方向の選択肢があるか**を判断するための材料を残すもの。具体的なマウントパス・接続情報・設定値などの実装詳細は設計（`docs/superpowers/specs/`）・実装計画（`docs/superpowers/plans/`）で定める。
>
> **表側仕様（利用者から見える動作）は保存先の切り替えに影響を受けない**ため、保存先を変えてもプロダクトADR（①〜④）の改訂は不要。

## 当初構成と、なぜそれを選んだか

カバー画像は、**サーバー（コンテナ）に永続ディスク（Volume）を1つ付け、そこに画像ファイルを置く**構成で運用を開始した。配信先サービス（Railway）のコンテナは再起動・再デプロイのたびに中身がリセットされるため、永続ディスクを使わないと画像が消える。

この「永続ディスク方式」を選んだ理由:

- **最小コストで永続化できる。** 外部ストレージの契約・認証情報の管理が不要で、ローカル開発の保存方法とほぼ同じまま本番で永続化できる。
- **今の規模（サーバー1台運用）に十分。** 凝った構成を持ち込まず、必要になってから拡張する（YAGNI）。

## 当初構成の限界

永続ディスクは**1台のサーバーに紐づく**ため、サービスを**複数台（複数インスタンス）に増やすと画像を共有できない**。増やした場合、片方で保存した画像がもう片方から見えず、「画像が出たり出なかったりする」不整合が起きる。したがって**この構成は単一インスタンス運用が前提**になる。

## 見直しトリガー（どれか1つでも該当したら再検討）

| トリガー | 具体的なシグナル | 何が問題になるか |
|---|---|---|
| **水平スケールの必要** | アクセス増でサーバーを複数台に増やしたい | 永続ディスクをインスタンス間で共有できず、画像表示が不整合になる |
| **高速配信（CDN）の必要** | 画像表示を世界各地で速くしたい／アプリ負荷を下げたい | アプリ経由・単一ノード配信では CDN を活かせない |
| **容量・コストの限界** | 画像が増え永続ディスクの容量・コストが見合わなくなる | ディスク増設より、従量課金のオブジェクトストレージが有利になりうる |
| **可用性・バックアップ要件** | 画像消失が許されない、世代バックアップが要る | 単一ディスク前提では冗長化・バックアップ運用の手当てが必要 |

## 取りうる代替案の方向性

永続ディスクで困るのは主に「複数台にスケールしたいとき」。その場合は**全インスタンスから共有アクセスできるオブジェクトストレージ**へ移すのが基本方針になる。

| 方向性 | 概要 | 向いている状況 | トレードオフ |
|---|---|---|---|
| **永続ディスク（当初構成）** | 1台のサーバーに永続ディスクを付けて保存 | 単一インスタンスで十分な規模 | 複数台に増やせない・CDN に不向き |
| **Railway のオブジェクトストレージ** | 配信先サービス内の S3 互換ストレージ | Railway 内で完結させたい | 認証情報の設定が要る |
| **Cloudflare R2** | 外部の S3 互換ストレージ。転送量（エグレス）無料 | 配信量が多くコストを抑えたい | 外部サービスの契約・管理が増える |
| **AWS S3** | 実績豊富な定番の S3 互換ストレージ | AWS 中心の構成・周辺サービス連携 | 転送量課金・AWS アカウント管理 |

いずれの S3 互換案も、全インスタンスから同じ画像を参照できるため**水平スケールと両立**し、CDN 配信にも発展できる。まずは永続ディスクで運用し、上記トリガーが顕在化してから、軽い順（Railway 内ストレージ → R2/S3）に検討する方針とした。先回りでの移行は YAGNI として避ける。

## 決定と移行記録（永続ディスク → Cloudflare R2）

- **実施日:** 2026-06-29（完了・本番反映済み）
- **移行前のリリース地点:** タグ `v6.4`（カバー画像機能まで／Cloudflare 対応の直前）
- **関連:** 設計書 `docs/superpowers/specs/2026-06-28-cover-image-r2-migration-design.md` ／ 実装計画 `docs/superpowers/plans/2026-06-28-cover-image-r2-migration.md`

> 上の「見直しトリガー」で挙げた条件が実際に該当したため、カバー画像の保存先を当初の**永続ディスク**から **Cloudflare R2**（オブジェクトストレージ）へ移行した。**利用者から見える動作（アップロードでき、一覧・詳細で表示される）は移行前後で変わらない。**

### なぜ移行したか

当初の永続ディスク方式には、運用上の制約があった。

- **デプロイのたびに短時間のサービス停止が起きていた。** 配信先サービス（Railway）の仕様上、サーバーに永続ディスクを付けていると、更新（デプロイ）のたびにディスクを付け替えるため、毎回わずかな停止時間が発生していた。
- **サーバーを増やせない。** 永続ディスクは1台のサーバーにしか紐づかず、アクセス増に備えて複数台に増やすと画像を共有できない（単一インスタンス前提）。
- **配信の高速化・コスト最適化の頭打ち。** アプリ経由・単一拠点の配信のため、CDN による高速化や転送コストの最適化ができない。

全サーバーから共有アクセスでき転送量（エグレス）無料の **Cloudflare R2** へ移すことで上記が解消し、**デプロイ時の停止がなくなり（ゼロダウンタイム化）**、将来の複数台運用・CDN 配信にも発展できる土台になった。

### 対応した内容（表側の変化なし）

- カバー画像の**保存先を永続ディスクから Cloudflare R2 へ変更**した。
- すでに保存されていたカバー画像を **R2 へ移し替え**た（消失なし・移行後の表示も確認済み）。
- カバー画像の**配信を R2 の公開 URL 経由**に切り替えた。

### 削除した内容

- サーバーに付けていた**永続ディスク（Volume）を撤去**した。これにより「単一インスタンス前提」と「デプロイのたびの停止」という制約がなくなった。

### ロールバック方針

- 移行前のリリース地点はタグ `v6.4`（Cloudflare 対応の直前）。問題が起きた場合はこのタグへ戻し、保存先設定を永続ディスクに切り替えることで復旧できる。保存先は設定（ディスク選択）で切り替えられる小改修としてあり、コードの再改修は不要。
- 具体的な手順・設定値は実装計画（`docs/superpowers/plans/2026-06-28-cover-image-r2-migration.md`）に記す。

### 現時点の留意点（暫定）

- 画像の公開 URL は、当面 **R2 が標準で発行する公開 URL** を使っている（独自ドメイン未取得のため。標準 URL は提供元が本番常用を非推奨としている）。独自ドメインを用意できれば、**画像の見え方・利用者の操作は変えずに**独自ドメイン配信へ切り替えられる（設定の差し替えのみで、画像の再移行は不要）。

## 表側仕様への影響

なし。利用者の操作・見え方は移行前後で変わらないため、プロダクトADR `../product/0004-event-cover-image.md` の決定（①〜④）の改訂は不要。

# 追加検討: アップロード画像のウィルス・不正ファイル対策

- **ステータス:** Proposed（提案・未決定。実装方式は、プロダクトADRで決まる要件レベルに応じて選ぶ）
- **日付:** 2026-07-05
- **位置づけ:** カバー画像の裏側の追加判断。保存先ストレージの決定（上記 Accepted）とは独立した論点で、**まだ実装していない**。ここに書くのは「どんなやり方があり、それぞれ何を得て何を払うか」までで、具体的な設定値・手順は採用決定後に実装計画（`docs/superpowers/plans/`）で定める。

## 背景と課題

カバー画像は現在、アップロードされたファイルを**中身の検査なしでそのまま保存**している。かかっているのは「画像形式か（jpeg/png/webp）」「5MB以下か」「寸法4000px以下か」というフォーマット上のチェックだけで、**ウィルスやマルウェア、画像に偽装した不正ファイルの検出はしていない。**

コミュニティ運営上、利用者が任意のファイルをアップロードできる口がある以上、「不正なファイルを保存・配信してしまう」リスクをどこまで手当てするかを決めておきたい。

## 前提: 「どこまで守るか」の要件はプロダクトADRで判断

次の3点は**利用者・運用ポリシーに関わる企画判断**のため、本ADR（技術）では決めず、プロダクトADR `../product/0004-event-cover-image.md`（追加検討: 不正ファイル対策の要件）で判断する。

- **守るレベル**: 「不正ファイルのアップロードを防ぐ」だけで十分か、「ウイルス検査の記録」まで要るか（コンプライアンス要件の有無）
- **プライバシー**: アップロード画像を外部サービスへ渡してよいか（社外にファイルが出る）
- **利用者体験**: その場で却下まででよいか、「保存直後は表示されない（検査後に公開）」まで許容するか

本ADRは、その**要件レベルを前提に、どの実装方式で満たすか（技術判断）**を扱う。コスト（従量課金 vs 常駐の固定費）と運用負荷（定義更新・監視）は、下記の実装方式A〜Dの比較に観点として含めている。

## まず確認: 利用中の各基盤に「組み込みのウィルスチェック」はあるか（調査結果）

ご依頼を受けて、現在使っている基盤に標準機能があるかを調べた。**結論: どれにも「アップロード画像をそのまま検査してくれる標準機能」はない。** いずれも自前で仕組みを足す必要がある。

| 基盤 | 組み込みのファイル・ウィルス検査 | 補足 |
|---|---|---|
| **Cloudflare R2**（現在の保存先） | **なし。** R2 に置いたファイルを自動スキャンする標準機能は提供されていない | R2 の「保存イベント」を起点に外部スキャンサービスを連携させる構成は可能。Cloudflare の別サービス（Zero Trust の通信スキャン）は R2 のファイルではなく通信を対象とするもので用途が違う |
| **Cloudflare WAF「悪意あるアップロード検知」** | **上位契約（Enterprise＋有料オプション）でのみ利用可**。通信を通過するファイルを検査 | ①最上位プラン限定、②**検知するだけで自動ブロックはしない**（別途ルールが必要）、③50MB超は先頭50MBのみ、といった制約あり。現契約では対象外 |
| **Railway**（現在の配信基盤） | **なし。** アプリを動かすだけの基盤で、ファイル検査機能は持たない | 自前のスキャン用サービス（例: ClamAV コンテナ）を追加して動かすことは可能 |
| **Docker** | **なし（用途が別）。** Docker の「スキャン」機能（Docker Scout）は、**配布するプログラムの部品に既知の脆弱性がないか**を調べるもので、利用者がアップロードした画像を検査するものではない | ただし ClamAV 等のスキャナを Docker コンテナとして動かす“入れ物”にはなる |

つまり、**「基盤の設定をONにすれば済む」わけではなく、次のいずれかの方式を自分たちで組み込む必要がある。**

## 検討した選択肢（実装方式）と、メリット・デメリット

> 画像アップロードでは「①画像として無害化する（サニタイズ）」と「②ウィルス定義でスキャンする」は別の対策で、片方だけ・両方の組み合わせのどれも取りうる。以下は軽い順。

### A. 画像の再エンコード（無害化 / サニタイズ）

アップロードされた画像を、いったんサーバー側で**開き直して作り直す**。見た目のピクセルだけを残して保存し直すことで、画像ファイルに紛れ込ませた不正なデータ（実行コードや細工されたメタ情報）を**そぎ落とす**。

- **メリット:** 画像アップロードで最も現実的な攻撃（画像に偽装した不正ファイル）に直接効く／**外部にファイルを出さない**／その場で完結しアップロードが失敗しにくい／ついでに画像を軽量化・形式統一できる
- **デメリット:** 「ウィルス定義に照らして検査した」という**記録は残らない**（あくまで無害化であって検出・記録ではない）／既知ウィルスそのものの“検知ログ”が要る要件は満たせない
- **プライバシー:** ◎（社外に出さない）／**コスト:** ◎（従量課金なし）／**運用:** ◎（定義更新など不要）／**利用者体験:** ◎（その場で完結）

> **「開き直すと感染するのでは？」への補足:** ここで言う「開く」は、画像の**色の情報だけを読み取る**作業で、ファイルの中身を**プログラムとして実行するわけではない**（コピー機が紙の見える部分だけを刷り直すのと同じ）。感染は「悪意あるコードが実行される」ことで起きるため、色を読み取るだけでは感染しない。むしろ再エンコードでは**色の情報だけを新しいファイルに作り直す**ので、画像に紛れ込ませた不正データは引き継がれず消える。なお現状のアップロードでも、形式・寸法チェックの時点で画像を同じように読み取っており、再エンコードで新たに危険が増えるわけではない（唯一の留意点は画像処理ライブラリ自体を最新に保つこと）。

### B. 自前のスキャン用サービスを常駐させる（オープンソースの ClamAV など）

ウィルススキャナ（ClamAV）を**自分たちのサーバー上に常駐**させ、保存前にファイルを検査する。

- **メリット:** **ファイルが社外に出ない**／利用回数あたりの**従量課金がゼロ**／定義ベースの本格的な検査と検知記録ができる／保存前にその場で弾ける
- **デメリット:** スキャナが**メモリを多く消費**し、常駐分の**固定費**がかかる／**ウィルス定義の自動更新や死活監視の運用**が必要／アップロードにやや時間がかかる
- **プライバシー:** ◎／**コスト:** △（常駐の固定費）／**運用:** △（定義更新・監視の手間）／**利用者体験:** ○（多少遅い）

> **Railway 上での置き方（2通り）:** ①**アプリと同じ入れ物に同居**させる（構成は単純だが、スキャナがアプリのメモリを圧迫し、アプリを増やすとスキャナも重複する）／②**スキャナを別サービスとして分ける**（アプリは軽いまま・複数台のアプリで1つのスキャナを共有できるが、常駐サービスが1つ増える）。いずれも、ウィルス定義を常にメモリに載せておく必要があり（数百MB〜1GB規模）、「使うときだけ起動」がしにくいため**メモリの固定費が恒常的にかかる**点は共通。

### C. 外部のスキャンサービスに委託する（従量課金のクラウドAPI）

アップロード時、または R2 の保存イベントを起点に、**外部のウィルススキャンサービス**（attachmentAV / bucketAV / Cloudmersive など）にファイルを送って判定してもらう。

- **メリット:** **自前サーバー・定義更新が不要**で導入が最も速い／検知記録も残る／定義の最新化は委託先任せ
- **デメリット:** **画像を社外サービスに送信する**（プライバシー・利用規約の確認が必要）／**利用回数に応じた従量課金**／外部サービスの応答待ち・障害時の挙動を設計する必要
- **プライバシー:** △（社外送信）／**コスト:** △（従量課金）／**運用:** ◎（お任せ）／**利用者体験:** ○（外部応答待ち）

> **外部サービスへ「いつ送るか」で2通り:** ①**保存する前に送る（同期）** = アップロード時にまず外部へ送って判定を待ち、合格したものだけ R2 に保存する。危険なファイルは**そもそも R2 に入らず一番安全**だが、判定を待つぶんアップロードが遅くなる。／②**R2 に保存してから送る（非同期）** = 先に保存し、保存イベントを起点に外部へ渡してスキャンし、危険なら後から削除・非公開にする。アップロードを待たせない反面、**判定が出るまでの短時間、危険なファイルが R2 に存在する**ため、公開URLで即配信する作りだとその隙に公開されうる。②を採るなら、まず非公開の隔離場所に保存し合格後に公開する **D（隔離公開）との併用が前提**になる。なお外部への渡し方は「アプリがAPIへ送る」「サービスに R2 の読み取り権限を渡して取りに来てもらう」のいずれか。

### D. スキャン結果が出るまで「隔離」してから公開する（配置の工夫・B/Cと併用）

上の B か C と組み合わせる**運用の型**。まず非公開の隔離場所に保存し、検査に合格したものだけを公開領域に移す。不合格は破棄して通知する。

- **メリット:** アップロード操作を待たせない／大きいファイルでも体験が安定／未検査の画像を利用者に見せずに済む
- **デメリット:** 仕組みが最も複雑／「**保存直後はまだ表示されない**」という状態の画面設計が必要／今の「5MB以下の画像限定」なら、そこまでせず A〜C の即時処理で十分間に合う（現時点では過剰になりやすい）
- **利用者体験:** 保存直後の表示が遅れる点をどう見せるかが要

## 推奨（Proposed 時のたたき台・決定はプロダクトオーナーに委ねる）

- **まず A（再エンコード）を土台として入れる**ことを推奨する。コストが最小で、画像アップロードで実際に起きやすい攻撃に一番効くため、「やらない理由がない」水準。プライバシー・運用・体験のいずれも損なわない。
- そのうえで、**プロダクトADRで決まる要件レベル（ウイルス検査記録の要否・外部送信の可否）に応じて** A に B か C を重ねる。**画像を社外に出せない**なら B（自前常駐）、**運用の手間を避けたく社外送信を許容できる**なら C（外部委託）。
- **D（隔離公開）は現時点では過剰**と判断。将来ファイルサイズ・種類が増えたときの発展案として残す。

## 決定

未定。**プロダクトADRで要件レベル（守るレベル・外部送信の可否・UX許容）が決まってから**、それを満たす実装方式（A〜D）を本欄で選び、ステータスを更新する。具体的な組み込み手順・設定は、そのあと実装計画（`docs/superpowers/plans/`）で定める。

## 表側仕様への影響（この追加検討分）

方式によって利用者から見える動作が変わりうる。A・B・C を保存前の即時処理として入れる場合は「不正なファイルはアップロードが**その場で却下される**」程度で、正常な画像の操作・見え方は変わらない。D（隔離公開）を選ぶ場合は「**保存直後はカバー画像がまだ表示されない**」という新しい見え方が生じるため、その時点でプロダクトADR `../product/0004-event-cover-image.md` の改訂が必要になる。
