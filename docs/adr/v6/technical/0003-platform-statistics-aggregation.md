# ADR-0003（技術）全体統計の集計方式

- **種別:** 技術ADR（開発者内部向け・裏側の実装判断）
- **ステータス:** Accepted
- **日付:** 2026-06-18
- **決定者:** 開発チーム
- **関連:** プロダクトADR `../product/0003-platform-statistics.md`（表側仕様＝見せる数字と数え方） / 設計書 `docs/superpowers/specs/2026-06-18-uc8-platform-statistics-design.md`

## このADRで決めること

プロダクトADR `../product/0003-platform-statistics.md` で確定した「運営者向け全体統計」の**裏側 = 数字をどう集計するか**を決める。あわせて、**現方式をいつ・なぜ見直すか（トリガー）と、取りうる代替案の方向性**を残す。

> このADRは「実装手順」そのものではなく、**後続の保守メンバーが現方式で運用できなくなったときに、いつ・なぜ見直し、どの方向の選択肢があるか**を判断するための材料を残すもの。具体的なスキーマ設計・バッチ構成・移行手順は実装計画（`docs/superpowers/plans/`）・設計（`docs/superpowers/specs/`）で定める。

## 決定（現方式）

**集計用テーブルを作らず、既存テーブル（`users` / `events` / `event_attendances`）を都度 `count` する。**

この方式を選んだ理由:

- **データ量が小さいうちはシンプルで正確。** 集計結果の鮮度管理や整合性担保が不要で、常に最新の実データを数えられる。
- **保守対象が増えない。** 集計テーブル・バッチ・キャッシュといった追加の可動部を持ち込まない（YAGNI）。

## 現方式の前提と限界

上記は「都度 count で十分軽い」ことを前提にしている。一方で、データ量の増加・アクセス増・データ保持要件の変化が進むと、この前提は次のいずれかで崩れる。

## 見直しトリガー（どれか1つでも該当したら再検討）

| トリガー | 具体的なシグナル | 何が問題になるか |
|---|---|---|
| **クエリレイテンシ超過** | ダッシュボード表示の集計クエリが基準（例: 1秒）を継続的に超える | 運営者の体感が悪化し「一目で把握」という目的が崩れる |
| **DB インスタンスの上限・コスト** | 全件 count のための CPU / IO 負荷でインスタンス増強が必要になる、コストが許容外になる | 規模把握のためだけに DB コストが膨らむ |
| **業務データと統計データの範囲の乖離** | 業務上は残す必要があるが統計には含めたくない（または逆）データが増える | 単純な全件 count では「見たい数字」を表せなくなる |
| **個人情報・履歴の保持期間整理** | 退会ユーザー・古い申込履歴の保持期間ポリシーを定める必要が出る | 物理削除・匿名化・アーカイブにより count 対象の定義自体が変わる |

これらは運用上の数値で判断するため、画面の挙動としては現れない。閾値（レイテンシ基準・コスト上限・保持期間）はプロジェクトの実情に合わせて運用側で定める。

## 取りうる代替案の方向性（段階的に検討）

下に行くほどコスト・複雑さが上がる。トリガーの深刻度に応じて軽い案から検討する。

| 方向性 | 概要 | 向いている状況 | トレードオフ |
|---|---|---|---|
| **短時間キャッシュ** | 集計結果を一定時間キャッシュし再計算頻度を下げる | レイテンシ/負荷が主因で、数字の即時性は多少犠牲にできる | 表示数字に最大キャッシュ時間分の遅延が出る |
| **集計テーブル（サマリーテーブル）** | 定期バッチ等で事前集計し、ダッシュボードはそれを読むだけにする | 全件 count が重く、推移グラフ等の拡張も見込む | 集計の鮮度管理・整合性担保・バッチ運用が増える |
| **読み取り用レプリカ / 分析用 DB の分離** | 統計クエリを本番 DB から切り離す | 業務トラフィックへの影響回避が主目的 | インフラ構成・コストが増える |
| **保持期間ポリシー＋アーカイブ** | 古い履歴をアーカイブ/匿名化し、統計対象を明確化する | 個人情報整理やデータ範囲の乖離が主因 | 数字の定義変更を伴い、過去との連続性に注意が必要 |

いずれも「現方式で問題が顕在化してから、トリガーに対応する最小の案を選ぶ」方針とする。先回りでの集計基盤構築は YAGNI として避ける。

## 表側仕様（数字の定義）への波及

代替案（特に保持期間ポリシー・アーカイブ）を採ると、プロダクトADR で確定した「数え方」（④）の意味が変わりうる。その場合は、**数字の定義変更を表側仕様の変更として プロダクトADR `../product/0003-platform-statistics.md` を改訂**（または後継 ADR で `Superseded`）し、レビューを経ること。実装都合だけで定義を黙って変えない。
