# ADR-0001 主催者リマインドのスコープと配信仕様

- **ステータス:** Proposed
- **日付:** 2026-06-14
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** 要件書 UC6（参加者にリマインドを届けたい・主催者視点）

## このADRで決めること

V6 で最初に作る「主催者 → 参加者へのリマインド」機能を、**どこまで作るか（スコープ）**を決める。

最小機能（後述の「土台」）を前提とし、その上に**追加候補（スケジュール送信・宛先選択・受信拒否設定）を今回入れるか**を、「便利さ」と「実装・保守コスト」のトレードオフで判断する。あわせて、入れると決めた機能の画面上の振る舞い（誰が送れるか・誰に届くか・結果をどう確認するか）を確定する。

> このADRは「最小機能 vs 高機能」の優劣を競うものではない。最小機能は必須で、論点は「**それ以上を今足すか**」にある。
>
> 裏側の作り（同期/非同期・テーブル構成・二重送信の防ぎ方など）は表側仕様ではないため、このADRには書かず実装計画（`docs/superpowers/plans/`）で定める。

## 背景と課題

誰でも無料でイベントを立てられる本サービスでは、主催者は無断キャンセルを減らしたい。また、開催直前の持ち物連絡・集合場所の案内・会場変更などを参加者へ届けたい。

現状、主催者から参加者への一斉連絡手段は存在しない。そこで「主催者 → 自分のイベント参加者全員」への連絡機能を追加する。

なお、これは要件書 UC3 の「システムが申込者本人に自動で送るリマインド」とは別物。UC6 は**主催者が送る運営連絡**であり、送信主体・宛先・目的が異なる。

## 判断の観点

追加候補を「入れる／見送る」を判断するため、各候補を次の観点で見る。

| 観点 | 説明 |
|---|---|
| **価値** | 誰が、どんなときに嬉しくなるか |
| **コスト** | 実装・保守の重さ（画面・ロジック・他機能との整合） |
| **確実性への影響** | 運営連絡（持ち物・会場変更）が参加予定者へ確実に届くことを、損なわないか |

「価値 > コスト で、確実性を損なわない」候補だけを今回入れる。

## 土台（必須・採用）

**最小手動** — 主催者が件名・本文を書いて、申込中の参加者へ手動で送る。送信後は受信者ごとの成否が見え、失敗した人だけ再送できる。

これは「主催者が参加者へ運営連絡を送る」という UC6 の最小UXをそのまま満たす。ここは議論の余地なく必須とし、論点は「これ以上を足すか」に絞る。

```
■ 土台（最小手動）の画面イメージ：主催者のイベント詳細ページ

  ── 参加者へのリマインド ──────────────────────
  件名: [ 【持ち物のお願い】Laravel勉強会 #5        ]
  本文: ┌──────────────────────────────────┐
        │ 明日はノートPCをお持ちください。      │
        │ 受付は18:30開始です。               │
        └──────────────────────────────────┘
  宛先: 申込中の参加者 12名         [ リマインドを送信 ]

  ── 配信履歴 ────────────────────────────────
  6/19 20:00  「【持ち物のお願い】…」  成功 11 / 失敗 1  [失敗分を再送]
  6/15 09:00  「会場変更のお知らせ」     成功 10 / 失敗 0
  ────────────────────────────────────────────
```

## 追加候補の評価（入れるか / 見送るか）

土台に何を足せるか。候補ごとに独立して評価する。

| 追加候補 | 何が嬉しくなるか（価値） | 追加コスト | 確実性への影響 | 判断 |
|---|---|---|:---:|:---:|
| **スケジュール送信** | 送り忘れを防げる。開催◯時間前に自動配信できる | 予約の保存・取消、開催時刻変更との整合、自動起動の仕組みが必要。UC3（システム自動リマインド）と機能が重なり責務が曖昧になる | 影響なし | **見送り**（YAGNI） |
| **宛先グループ選択**（キャンセル待ちも含める等） | 繰り上げ前提でキャンセル待ちにも連絡できる | 宛先選択UI、対象抽出の分岐、配信履歴に「どの宛先条件で送ったか」を記録する複雑さが増える | 影響なし | **見送り**（YAGNI） |
| **受信拒否設定** | 参加者が不要なメールを止められる | プロフィールに設定画面、配信時の除外判定が必要 | **下がる**（当日の持ち物・会場変更が届かない人が出る） | **不採用**（逆効果） |

```
■ 追加候補を入れた場合に増える画面（参考）

  ＜スケジュール送信＞
    送信タイミング: ○今すぐ  ○開催24時間前   ← 予約欄が増える

  ＜宛先グループ選択＞
    宛先: ○申込中のみ  ○キャンセル待ちも含む  ← 宛先選択が増える

  ＜受信拒否設定＞（参加者側のプロフィール）
    □ 主催者からのリマインドを受け取らない   ← 設定項目が増える
```

### 判断の根拠（見送りと不採用は理由が違う）

見送る理由は2種類あり、混同しないよう分けて記す。

- **スケジュール送信 / 宛先グループ選択 → 見送り（YAGNI）**
  便利だが、今は実装・保守コストに見合わない。まず手動で運用し、「送り忘れが多い」「キャンセル待ちにも連絡したい」という必要性が実際に出てから段階的に足せる。特にスケジュール送信は UC3（システム自動リマインド）と仕組みが重なるため、UC3 を作るときに統合して設計する方が筋が良い。**「不要」ではなく「今はやらない」。**

- **受信拒否設定 → 不採用（逆効果）**
  これは便利さの問題ではなく、運営連絡という性質に合わない。持ち物・会場変更・集合時間といった当日連絡を参加者が拒否できると、肝心の連絡が届かずかえって参加者が困る。広告メールではないため拒否の必要性も低い。**コストの問題ではなく、入れること自体が目的に反する。**

## 推奨と理由（たたき台）

**土台（最小手動）のスコープで作り、追加候補はいずれも今回入れない。**

- 土台だけで UC6 の目的（主催者が参加者へ運営連絡を届ける）は満たせる。
- スケジュール送信・宛先選択は「便利だが今はコストに見合わない」ため見送り、必要性が実証された段階で足す（YAGNI）。
- 受信拒否設定は「運営連絡には逆効果」のため不採用。
- 送信結果は受信者ごとに成否が見え、失敗した人だけ再送できるので、追加機能なしでも確実に全員へ届けきれる。

## 宛先がいつ確定するか（よくある疑問）

主催者が「送信」を押した**瞬間の申込中（Applied）の参加者**を宛先として固定する（写真を撮るように記録する）。以後の参加状態の変化では、その配信の宛先は変わらない。

```
■ 送信中にキャンセル待ちから繰り上がった人
  → そのリマインドには含まれない（次に送るリマインドで届く）
     理由: 画面に「12名に送信」と出た通りの人に届く一貫性を優先する

■ リマインドが届いた後にキャンセルした人
  → 届いたメールは取り消せない。配信履歴には「成功」として残る
     （「6/19 20:00 時点で申込中だった人に送った」という事実は変わらない）

■ 送信を押した直後〜実際に届くまでの数秒〜数分でキャンセルした人
  → そのまま届く（押した瞬間の宛先リストに忠実）
```

これは「申込中の人へ送る」という主催者の意図を、**「送信を押した時点で申込中だった人」**と解釈する決め。送信中に人数が動いて「12名と表示されたのに実際は13名に届いた」というズレを防ぐ。

## 決定

（レビュー待ち。承認時に理由とともに記入する。）

ブレストでの合意済み内容を推奨として記載:
- スコープ → **土台（最小手動）のみ。スケジュール送信・宛先選択は見送り、受信拒否設定は不採用。**
- いつ送れるか → **手動送信のみ**
- 誰に届くか → **申込中（Applied）の参加者のみ**
- 受信拒否 → **設けない**（運営連絡のため必ず受信）
- 結果確認 → **受信者ごとに成否を表示し、失敗分のみ再送できる**
- 送信できる人 → **主催者（オーナー＋承諾済み合同主催者）**。V5 で「編集・出欠記録」ができる人と同じ範囲。オーナーがメールを送れない状況でも、合同主催者が代理で連絡を送れるようにするため、合同主催者にも許可する。
- 宛先の確定 → **送信ボタンを押した時点の申込中の参加者で固定**。送信中に繰り上がった人は次回対象。送信後にキャンセルしても、届いたメールと配信履歴は残る。

## 影響・結果

- **採用＝土台のみの場合、ユーザーから見える動き:**
  - 主催者（オーナー／承諾済み合同主催者）のイベント詳細ページに「参加者へのリマインド」送信フォームと「配信履歴」が表示される。
  - 申込中の参加者は、主催者が送ったリマインドメールを受け取る。受信拒否はできない。
  - 主催者は配信ごとに「成功◯名・失敗◯名」を確認でき、失敗した参加者だけ再送できる。
  - キャンセル済み・キャンセル待ちの人にはリマインドは届かない。
  - スケジュール送信・宛先選択の画面は出ない（将来必要になれば追加）。
- 見送った候補（スケジュール送信・宛先選択）は、必要性が実証されたら別バージョンで再検討する。スケジュール送信は UC3 実装時に統合を検討する。
- 具体的な実装方法（非同期ジョブ・送信履歴の持ち方・二重送信の防ぎ方）は、採用が決まってから実装計画（`docs/superpowers/plans/`）で定める。
