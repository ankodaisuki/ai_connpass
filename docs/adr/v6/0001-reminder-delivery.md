# ADR-0001 主催者リマインドの配信仕様

- **ステータス:** Proposed
- **日付:** 2026-06-14
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** 要件書 UC6（参加者にリマインドを届けたい・主催者視点）

## このADRで決めること

主催者が自分のイベントの参加者へ**リマインドメールを送る機能**について、画面から見える振る舞いを決める。具体的には次の4点。

1. **いつ送れるか**（主催者が手動で送る／開催前に自動で送る）
2. **誰に届くか**（申込中の人だけ／キャンセル待ちにも）
3. **参加者は受信を拒否できるか**（opt-out の有無）
4. **主催者は送信結果をどこまで確認できるか**

> 裏側の作り（同期/非同期・テーブル構成・二重送信の防ぎ方など）は表側仕様ではないため、このADRには書かず実装計画（`docs/superpowers/plans/`）で定める。

## 背景と課題

誰でも無料でイベントを立てられる本サービスでは、主催者は無断キャンセルを減らしたい。また、開催直前の持ち物連絡・集合場所の案内・会場変更などを参加者へ届けたい。

現状、主催者から参加者への一斉連絡手段は存在しない。そこで「主催者 → 自分のイベント参加者全員」への連絡機能を追加する。

なお、これは要件書 UC3 の「システムが申込者本人に自動で送るリマインド」とは別物。UC6 は**主催者が送る運営連絡**であり、送信主体・宛先・目的が異なる。

## 決定ドライバー

| # | 判断基準 | 説明 |
|---|---|---|
| D1 | 当日連絡の確実性 | 持ち物・会場変更などの連絡が、参加予定者へ確実に届くか |
| D2 | 主催者の使いやすさ | 必要なときにすぐ送れるか。画面が複雑でないか |
| D3 | 参加者の負担・信頼 | 不要なメールで負担をかけないか。拒否の余地が要るか |
| D4 | 実装・運用コスト | V6 の最初の機能として無理のない範囲か |

## 検討した選択肢

- **案A 最小手動** — 主催者が件名・本文を書いて手動送信。宛先は申込中の人のみ。受信拒否設定なし。送信後は受信者ごとの成否が見え、失敗した人だけ再送できる。
- **案B スケジュール追加** — 案A に加え、「開催◯時間前に自動配信」を事前予約できる。
- **案C 高機能** — 案A に加え、参加者がリマインド受信を拒否できる設定や、宛先グループ（キャンセル待ちも含める等）の選択を持つ。

## 各案の比較

評価記号: ◎=強い / ○=可 / △=弱い / ▲=コスト高

| 観点 | 案A 最小手動 | 案B スケジュール追加 | 案C 高機能 |
|---|:---:|:---:|:---:|
| D1 当日連絡の確実性 | ◎ 全員に届く | ◎ | △ 拒否で届かない人が出る |
| D2 主催者の使いやすさ | ◎ シンプル | ○ 予約UIが増える | △ 宛先選択が増える |
| D3 参加者の負担・信頼 | ○ 運営連絡のみ | ○ | ◎ 拒否できる |
| D4 実装・運用コスト | ◎ 最小 | ▲ 予約・自動起動が必要 | ▲ 設定・除外ロジックが必要 |

**案A 最小手動**
- ＋ 申込中の全員に確実に届く（D1）。運営連絡（持ち物・会場変更）は本来届くべき性質で、opt-out で当日連絡が届かない事故を避けられる。
- ＋ 「書いて送る」だけで画面がシンプル（D2）。V6 最初の機能として無理がない（D4）。
- − 開催前の自動送信はできない（毎回手動）。

**案B スケジュール追加**
- ＋ 送り忘れを防げる。
- − 予約の保存・取消、開催時刻変更との整合、自動起動の仕組みが必要でコストが高い（D4）。UC3（システム自動リマインド）と機能が重なり、責務が曖昧になる。

**案C 高機能**
- ＋ 参加者が受信を拒否でき、宛先も柔軟（D3）。
- − 運営連絡（当日の持ち物・会場変更）まで拒否されると届かず、かえって参加者が困る（D1）。設定・除外ロジックの実装コストも高い（D4）。

## 推奨と理由（たたき台）

**案A 最小手動を推奨。**

- 運営連絡は申込者へ確実に届くべきで、opt-out を設けないことで「当日連絡が届かない」事故を防げる（D1・D3）。マーケティングメールではないため拒否の必要性は低い。
- 宛先を「申込中のみ」に絞ることで、キャンセル済み・キャンセル待ちへ誤って送る事故を避けられる（D1）。
- 「件名・本文を書いて送る」だけの最小画面で主催者がすぐ使える（D2）。
- 送信結果は受信者ごとに成否が見え、失敗した人だけ再送できるため、確実に全員へ届けきれる（D1）。
- スケジュール送信（案B）・受信拒否や宛先選択（案C）は、運用しながら必要性が固まった段階で段階的に追加できる。

## 決定

（レビュー待ち。承認時に理由とともに記入する。）

ブレストでの合意済み内容を推奨として記載:
- いつ送れるか → **手動送信のみ**
- 誰に届くか → **申込中（Applied）の参加者のみ**
- 受信拒否 → **設けない**（運営連絡のため必ず受信）
- 結果確認 → **受信者ごとに成否を表示し、失敗分のみ再送できる**
- 送信できる人 → **主催者（オーナー＋承諾済み合同主催者）**。V5 で「編集・出欠記録」ができる人と同じ範囲。

## 影響・結果

- **採用＝案A の場合、ユーザーから見える動き:**
  - 主催者（オーナー／承諾済み合同主催者）のイベント詳細ページに「参加者へのリマインド」送信フォームと「配信履歴」が表示される。
  - 申込中の参加者は、主催者が送ったリマインドメールを受け取る。受信拒否はできない。
  - 主催者は配信ごとに「成功◯名・失敗◯名」を確認でき、失敗した参加者だけ再送できる。
  - キャンセル済み・キャンセル待ちの人にはリマインドは届かない。
- 具体的な実装方法（非同期ジョブ・送信履歴の持ち方・二重送信の防ぎ方）は、採用が決まってから実装計画（`docs/superpowers/plans/`）で定める。
