# ADR-0003 運営者向け全体統計の仕様

- **ステータス:** Accepted
- **日付:** 2026-06-18（提案）
- **決定者（レビュー）:** プロダクト責任者 / 企画
- **関連:** 要件書 UC8（全体統計）、ADR-0002（不適切対処・運営者ロール）

## このADRで決めること

V6 で導入する「**運営者（プラットフォーム運営）**」が、サービス全体の状況を把握するための**全体統計画面の見え方**を決める。

具体的には次の判断を確定する。

- その統計を誰が見られるか
- どんな数字を見せるか
- どんな見せ方（今の総数だけか、推移も見せるか）にするか
- それぞれの数字を何の数として数えるか

> 裏側の作り（数字の集計方法・キャッシュの有無・テスト方法など）は表側仕様ではないため、このADRには書かず実装計画（`docs/superpowers/plans/`）と設計（`docs/superpowers/specs/`）で定める。

## 背景と課題

V6 で運営者が不適切対処（ADR-0002）を担うようになると、運営者は「いまサービスがどれくらいの規模で動いているか」を把握したくなる。利用者数・イベント数・参加申込数といった全体像が分からないと、運用の判断材料が持てない。

そこで運営者向けに、サービス全体の規模を一目で確認できる統計画面を設ける。最初の一歩として「現状を素早く把握できる最小限の数字」を提供することを目的とし、凝った分析機能は持たない。

## 判断の観点

| 観点 | 説明 |
|---|---|
| **把握のしやすさ** | 運営者がサービス規模を一目で掴めるか |
| **見える範囲の妥当性** | 統計を見られる人が適切か（運営者に限られるか） |
| **コスト** | 画面・数字の作り込みの重さ |

## 土台（必須・採用）

**運営者がサービス全体の規模（数字）を確認できる。** これは UC8 の最小要件であり議論の余地なく必須とする。論点は「どの数字を・どんな見せ方で・誰に出すか」に絞る。

## 決定事項ごとの選択肢評価

### ① 誰が見られるか

| 選択肢 | 妥当性 | 判断 |
|---|:---:|:---:|
| 運営者のみ | 高（運用判断のための内部数字） | **採用** |
| 主催者にも自分向けの統計を出す | 別目的（主催者の集客分析）で UC8 の範囲外 | 見送り |
| 一般公開（トップページ等に実績数字） | 別目的（マーケ・信頼性訴求）で UC8 の範囲外 | 見送り |

全体統計は運営判断のための内部数字とし、運営者だけが見られる。一般利用者には統計画面・数字は一切表示されない。主催者向け・一般公開向けの数字は目的が異なるため、必要になれば別途検討する。

### ② どんな数字を見せるか

| 選択肢 | 把握のしやすさ | コスト | 判断 |
|---|:---:|---|:---:|
| ユーザー数・イベント数・申込数の3つ | 高（規模の三本柱） | 小 | **採用** |
| 上記＋運営対処実績（凍結数・削除数） | 高だが目的が混ざる | 中 | 見送り |

サービス規模を表す「ユーザー数・イベント数・参加申込数」の3つに絞る。運営対処の実績（凍結・削除の件数）は ADR-0002 の監査ログで個別に追える領域であり、規模把握とは目的が違うため全体統計には含めない。

### ③ どんな見せ方にするか

今の総数だけを並べる「スナップショット」か、月ごとの増減を折れ線などで見せる「推移」かを決める。

```
■ 採用案: スナップショット（今の総数だけ）
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ ユーザー  │ │ イベント  │ │ 申込     │
   │  1,234   │ │   567    │ │  8,900   │
   │ 総登録数  │ │ 総数      │ │ 有効申込  │
   └──────────┘ └──────────┘ └──────────┘

■ 見送り案: 推移グラフ（月ごとの増減）
   ユーザー数の推移
   1500┤                    ╭──
   1000┤            ╭───────╯
    500┤   ╭───────╯
      └─────────────────────────
       1月  2月  3月  4月  5月
```

| 選択肢 | 把握のしやすさ | コスト | 判断 |
|---|:---:|---|:---:|
| 現在の総数のスナップショットのみ | 規模は一目で分かる | 小 | **採用** |
| 月別などの推移グラフも見せる | トレンドも分かる | 中〜大（期間集計・グラフ描画） | 見送り（YAGNI） |

まずは「今どれくらいの規模か」を最小コストで出す。推移（トレンド）が必要になってから段階的に足す。

### ④ それぞれの数字を何の数として数えるか

各カードに出す数字の「意味」を確定する（利用者から見える数字の定義のため表側仕様に含める）。

| 数字 | 数え方 | 補足 |
|---|---|---|
| **ユーザー数** | これまでに登録された全アカウント数 | 状態（有効・未有効）を問わず合算した総登録数 |
| **イベント数** | 今あるイベントの総数 | 下書き・非公開・公開を区別せず合算。削除されたイベントは含めない |
| **申込数** | 現在有効な参加申込の数 | キャンセル済み・キャンセル待ちは含めず、有効な申込だけを数える |

「総数を素早く把握する」目的に合わせ、ユーザー数とイベント数は状態を分けずまとめた総数とする。申込数だけは「実際に参加する意思のある有効な申込」を見たいため、キャンセル・キャンセル待ちを除いた数とする。状態別の内訳が必要になれば後から足す。

## 画面イメージ（参考）

```
/admin（運営ダッシュボード・トップ）

 ── 運営ダッシュボード ─────────────────────
   ┌──────────┐ ┌──────────┐ ┌──────────┐
   │ ユーザー  │ │ イベント  │ │ 申込     │
   │  1,234   │ │   567    │ │  8,900   │
   │ 総登録数  │ │ 総数      │ │ 有効申込  │
   └──────────┘ └──────────┘ └──────────┘
 ────────────────────────────────────────
```

運営者がログインして最初に開く運営画面のトップに、この3枚のカードを表示する。一般利用者にはこの画面自体が見えない。

## 推奨と理由（たたき台）

**運営者のみが見られる画面で、ユーザー数・イベント数・有効な申込数の3つを、現在の総数のスナップショットとして表示する。**

- 運営者がサービス規模を一目で把握できる、という UC8 の目的を最小コストで満たせる。
- 運営対処実績・推移グラフ・主催者向け/一般公開向けの数字は目的が異なる、または重いため見送り、必要性が出てから足す（YAGNI）。
- どの数字も「総数の素早い把握」に最適化し、申込数のみ有効な申込に絞ることで実態に近づける。

## 決定

推奨案をそのまま採用する。

確定した仕様:
- 見られる人 → **運営者のみ。一般利用者・主催者には表示しない。**
- 見せる数字 → **ユーザー数・イベント数・有効な申込数の3つ。運営対処実績は含めない。**
- 見せ方 → **現在の総数のスナップショットのみ。推移グラフ・期間集計は持たない。**
- 数え方 → **ユーザー数＝総登録数（状態問わず）／イベント数＝総数（削除を除く全状態）／申込数＝有効な申込のみ（キャンセル・待ちを除く）。**
- 配置 → **運営ダッシュボード（運営画面のトップ）。**

## この決定を見直すとき（移行トリガーと代替案）

> このセクションは「実装手順」ではなく、**後続の保守メンバーが現仕様で運用できなくなったときに、いつ・なぜ見直し、どの方向の選択肢があるか**を判断するための材料を残すもの。具体的なスキーマ設計・バッチ構成・移行手順は採用決定後に実装計画（`docs/superpowers/plans/`）で定める。

### 現仕様の前提と限界

本統計は「集計用テーブルを作らず、既存テーブル（users / events / event_attendances）を都度 count する」方針を採る。データ量が小さいうちはシンプルで正確、かつ保守対象が増えないという利点がある。一方で、データ量の増加・アクセス増・データ保持要件の変化が進むと、この前提は次のいずれかで崩れる。

### 見直しトリガー（どれか1つでも該当したら再検討）

| トリガー | 具体的なシグナル | 何が問題になるか |
|---|---|---|
| **クエリレイテンシ超過** | ダッシュボード表示の集計クエリが基準（例: 1秒）を継続的に超える | 運営者の体感が悪化し「一目で把握」という目的が崩れる |
| **DB インスタンスの上限・コスト** | 全件 count のための CPU / IO 負荷でインスタンス増強が必要になる、コストが許容外になる | 規模把握のためだけに DB コストが膨らむ |
| **業務データと統計データの範囲の乖離** | 業務上は残す必要があるが統計には含めたくない（または逆）データが増える | 単純な全件 count では「見たい数字」を表せなくなる |
| **個人情報・履歴の保持期間整理** | 退会ユーザー・古い申込履歴の保持期間ポリシーを定める必要が出る | 物理削除・匿名化・アーカイブにより count 対象の定義自体が変わる |

これらは運用上の数値で判断するため、画面の挙動としては現れない。閾値（レイテンシ基準・コスト上限・保持期間）はプロジェクトの実情に合わせて運用側で定める。

### 取りうる代替案の方向性（段階的に検討）

下に行くほどコスト・複雑さが上がる。トリガーの深刻度に応じて軽い案から検討する。

| 方向性 | 概要 | 向いている状況 | トレードオフ |
|---|---|---|---|
| **短時間キャッシュ** | 集計結果を一定時間キャッシュし再計算頻度を下げる | レイテンシ/負荷が主因で、数字の即時性は多少犠牲にできる | 表示数字に最大キャッシュ時間分の遅延が出る |
| **集計テーブル（サマリーテーブル）** | 定期バッチ等で事前集計し、ダッシュボードはそれを読むだけにする | 全件 count が重く、推移グラフ等の拡張も見込む | 集計の鮮度管理・整合性担保・バッチ運用が増える |
| **読み取り用レプリカ / 分析用 DB の分離** | 統計クエリを本番 DB から切り離す | 業務トラフィックへの影響回避が主目的 | インフラ構成・コストが増える |
| **保持期間ポリシー＋アーカイブ** | 古い履歴をアーカイブ/匿名化し、統計対象を明確化する | 個人情報整理やデータ範囲の乖離が主因 | 数字の定義変更を伴い、過去との連続性に注意が必要 |

いずれも「現仕様で問題が顕在化してから、トリガーに対応する最小の案を選ぶ」方針とする。先回りでの集計基盤構築は YAGNI として避ける。

### 数字の定義への波及

代替案（特に保持期間ポリシー・アーカイブ）を採ると、ADR 上で確定した「数え方」（④）の意味が変わりうる。その場合は数字の定義変更も**表側仕様の変更**として本 ADR を改訂（または後継 ADR で `Superseded`）し、レビューを経ること。実装都合だけで定義を黙って変えない。

## 影響・結果

- **ユーザーから見える動き:**
  - 運営者は運営画面のトップで、ユーザー数・イベント数・有効な申込数の現在の総数を確認できる。
  - 一般の利用者には統計画面・数字は一切見えない。
- 本機能は ADR-0002 で導入する運営者ロール・運営画面（`/admin`）に乗せるため、**UC7 を先に実装する前提**とする。
- 見送った候補（推移グラフ・運営対処実績・主催者向け/一般公開向け統計）は、必要性が実証されたら別バージョンで再検討する。
- 具体的な実装方法（数字の集計方法・整形・テスト）は、採用が決まってから設計（`docs/superpowers/specs/2026-06-18-uc8-platform-statistics-design.md`）と実装計画（`docs/superpowers/plans/`）で定める。
