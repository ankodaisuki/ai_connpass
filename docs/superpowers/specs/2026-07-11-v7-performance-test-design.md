# v7 性能試験・ロングランテスト計画（設計）

- **作成日:** 2026-07-11
- **ステータス:** 提案段階（メンターレビュー待ち。承認後に実装計画を作成）
- **目的:** ユーザーが継続的に操作したときにメモリ使用量が異常に増えないか、サーバースペックが足りるか、特定機能がボトルネックにならないかを、実際の使われ方を前提としたシナリオで検証する計画を定める。

## スコープ

### 含むもの

- 画面・API 全ルートの洗い出しと試験対象の選定（「試験対象の選定」の MECE 表を参照）
- 申込スパイク試験（短時間・高負荷）の計画
- 24時間ロングランテスト（定常負荷）の計画
- 負荷モデル（想定規模と RPS の導出根拠）
- 判断基準（SLO）とレポート方法

### 含まないもの（スコープ外）

- **DDoS・悪意ある異常系:** まず通常利用の性能試験を行い、結果のリスクマトリクスから「攻撃されたら危ないエンドポイント」が見えた時点で対策要否を判断する。
- **ツール選定と実装:** 本計画の承認後、次のステップとして実施する。候補は k6 / Locust / Gatling を想定。
- **Google Calendar 実 API への負荷:** 外部サービスのため対象外。含める場合もモック前提。

## 前提

- **実行環境:** Railway（無料プラン）の本番環境（単一サービス、MySQL 8.4）で**そのまま実施**する。この構成が想定規模（connpass 級）に耐えない見込みが高いことは織り込み済みで、限界点の特定とスケール改善の入力を得ることが試験の主目的（「テスト実行方針」「負荷モデル」の節を参照）
- **アーキテクチャ上の急所:** セッション・キュー・キャッシュがすべて同一 MySQL（`SESSION_DRIVER=database` / `QUEUE_CONNECTION=database` / `CACHE_STORE=database`）。1リクエストあたり複数の DB 書き込みが発生するため、低めの RPS でも DB が中心的なボトルネック候補になる。
- **静的アセット:** カバー画像は R2 配信のため負荷対象外。動的リクエスト（PHP 処理）のみを対象とする。

## テスト実行方針

- **実行環境: Railway（無料プラン）でそのまま実施し、あえて壊れるくらいの負荷をかける。**
- **位置づけ:** サーバースペック選定は本来「想定負荷に耐えられるスペックを逆算する」考え方で行う。今回はその逆で、**弱いサーバーに先に限界を迎えさせ、原因（DB 接続部分か・内部処理か等）を特定する練習**として実施する。弱い環境ほど早くボトルネックが顕在化するため、原因切り分けの学習効率が高い。
- **即死時のプロトコル:** ピーク負荷でサーバーが即死しても、そこで試験終了とはしない。**負荷を段階的に下げて計測可能な帯域を見つけ、レポーティングまで必ずやり切る**。「何 RPS までなら生きられるか」自体が主要成果物のため、壊れた事実だけで終わらせない（限界探索ランプを先に実施するのも同じ理由）。
- **実施する試験は2種:** ロングラン（平均的な持続負荷 3〜5 RPS × 24時間でメモリリーク等の実践面の不具合を検出）と、スパイクテスト（connpass 級の瞬間高負荷でどこが・何が原因で壊れるかを特定）。詳細は「試験1」「試験2」の節。

## シナリオのモデル化方針（採用: ハイブリッド型）

検討した3案から**案C（ハイブリッド）**を採用する。

| 案 | 概要 | 判断 |
|---|---|---|
| A: ユーザージャーニー型 | 仮想ユーザーの一連の行動（ログイン→閲覧→申込→確認）をモデル化 | 主軸として採用 |
| B: エンドポイント単体ベンチ | 個別エンドポイントの限界 RPS を測る | 深掘り手順として補助採用 |
| **C: ハイブリッド（採用）** | A を主軸に、問題が出た箇所だけ B で限界値を特定 | **採用** |

採用理由: セッション・キュー・キャッシュが同一 MySQL に乗る構成では、複合負荷でこそボトルネックが現れる。一方で「どの機能が危ないか」の判定には問題箇所の単体限界値が説得力を持つため、両方を組み合わせる。

## 負荷モデル（規模 → RPS の導出）

### 試験規模の方針（なぜ現状の利用実績より大きい規模で試験するか）

個人開発で利用実績がないため、シナリオは仮想で決める前提。その上で**現状規模ではなく数ヶ月後に到達しうる想定規模（connpass 級）で初期構築時点から試験する**。

理由: 初期構築時点はエンジニアの体制・知識が最も厚い。後から急にスケールが必要になった際に、対応できるエンジニアを確保できる保証はなく、仕様伝達のコミュニケーションコストもかかる。潰せるボトルネックは体制が厚いうちに早めに潰しておく。また、小さい規模（無料サーバーで余裕のある負荷）で試験しても何もボトルネックが見つからずに終わり、試験の学びがない。

### 想定規模（connpass 公表値ベース）

通常時のトラフィックは connpass の公表値（月間PV）から導出する:

| 項目 | 値 | 導出 |
|------|------|------|
| 月間PV | 2,455,000 | 公式 |
| 日平均PV | 約81,800 | 月間PV ÷ 30 |
| 平均PV/秒 | 約0.95 | 日平均PV ÷ 86,400 |
| ピーク時PV/秒 | 約3〜5 | 日次PVの10〜15%が最ピーク1時間に集中＋平日係数 |
| アプリへの実RPS | ピーク 3〜5 RPS（平均 約1 RPS） | 1PV ≒ **1動的リクエスト**（下記「本アプリの1PVの実態」） |

### 本アプリの1PVの実態（PV→リクエスト換算の根拠）

「1PV ≒ 3〜5リクエスト（HTML＋API＋非同期）」は SPA 前提の一般値であり、本アプリには当てはまらない（メンターレビュー 2026-07-15 反映）。コードで確認した実態:

- Blade のサーバーサイドレンダリングで、1ページ表示 ＝ **HTML を返す動的リクエスト1本**
- AJAX / API 呼び出しは**ゼロ**（`fetch`・`axios`・XHR がコードに存在せず、`resources/js/app.js` は実質空）
- CSS/JS は nginx が直接配信（`docker/nginx.conf` の `try_files`）で PHP / MySQL に到達しない。画像は R2 配信

したがって **1PV ≒ 1動的リクエスト（換算係数1）**。ピーク実RPS ＝ 3〜5 PV/秒 × 1 ≒ **3〜5 RPS**、平均実RPS ≒ **約1 RPS**。将来 API・非同期処理を追加した場合はこの係数から見直す。

スパイクシナリオ用の追加想定:

| 項目 | 想定値 | 根拠 |
|---|---|---|
| 同時公開中イベント | 5,000件 | 仮定（connpass 規模の月間開催イベント数の規模感） |
| 超人気イベント | 定員2,000の大型カンファレンス。**内訳: 会場（オフライン）200人＋オンライン1,800人のハイブリッド開催** | 会場のみで2,000人収容は国内では非現実的。大規模カンファレンスはオンライン枠が大半を占めるハイブリッドが実態 |
| 申込殺到の規模 | 受付開始10分間に約3,000人が申込を試み、最初の1分に1,500人が集中 | 「超人気時は通常の100倍」ルールとの整合（RPS の導出を参照） |

> **実装上の注記:** 本アプリは1イベント1定員（`events.capacity`）で、connpass のような参加枠の内訳（現地枠/オンライン枠）を持たない。そのため試験上は**合計2,000人の単一枠**として扱う（申込 POST の負荷・定員整合性の検証は枠の内訳に依存しない）。対象イベントは `online_url` を設定したハイブリッド相当としてシードする。将来参加枠機能を実装した場合は、枠ごとの定員カウントが競合点になるため試験の見直しが必要。

### ジャーニーの定義

1人の申込ジャーニー ＝ ログイン(2リクエスト) → イベント詳細閲覧(2〜3回・リロード含む) → 申込POST(1) → マイページ確認(1) ＝ **約7動的リクエスト/人**。

### RPS の導出

**基本ロジック:** 月間想定数 → 日次換算 → 秒あたり（1日の秒数 86,400 で割る）→ ピーク時はそこからさらに数倍で見積もる。上表（想定規模）の PV → 実RPS 換算がこのロジックの適用そのものである:

```
月間PV 2,455,000（公式） → ÷30 ≒ 日平均PV 81,800
→ ÷86,400秒 ≒ 平均 0.95 PV/秒
→ ピーク集中（日次PVの10〜15%が最ピーク1時間＋平日係数） ≒ 3〜5 PV/秒
→ × 1リクエスト/PV（Blade SSR・「本アプリの1PVの実態」参照） ≒ ピーク実RPS 3〜5
```

なおピーク集中率（10〜15%）は仮定値である。重要なのは数字そのものより導出過程が式で残っていることで、実サービス化後はアクセスログの実測値で係数を差し替えれば負荷モデルを更新できる。

- **スパイクピーク:** 「超人気時は通常の100倍」ルールを平均実RPS（約1）に適用 → **計画値 100 RPS**。ジャーニーによる裏取り: 最初の1分に1,500人が集中 × 約4リクエスト/分 ÷ 60秒 ≒ 100 RPS（うち申込 POST 10〜20 RPS、残りは閲覧・認証）
- **スパイク持続（続く10分・残り約1,500人＋キャンセル待ち申込＋リロード様子見）:** 約 **10〜20 RPS**
- **背景負荷:** 通常閲覧 3〜5 RPS（日常ピーク帯）を常時混入
- **ロングラン定常:** **3〜5 RPS** を24時間継続 ＋ 1時間おきに 10 RPS（日常ピークの2〜3倍）× 5分の小ピーク。3〜5 RPS は新換算では日常ピーク帯相当の持続負荷（平均約1 RPSより安全側）。ロングランの目的は限界性能ではなく経時劣化の検出のため、このレベルで十分

### この規模設定が試験の目的に与える影響

現行構成（Railway 無料プラン単一サービス＋セッション/キュー/キャッシュ同居の単一 MySQL）がスパイク要求の 100 RPS に耐えられない可能性が高い。したがってこの試験の問いは「**耐えられるか**」ではなく:

1. **どこから壊れるか** — 何 RPS で・どの機能が・どういう壊れ方（遅延/5xx/整合性破壊）をするかの特定（＝限界 RPS の実測）
2. **スケールさせるには何を変えるべきか** — ボトルネックの序列を明らかにし、改善（Redis 分離、コネクションプール、リードレプリカ、水平スケール等）の優先順位の根拠を得る

## 試験対象の選定（画面・API 一覧）

全ルート（41本 = 現行39本 ＋ PR #28 で追加予定の2本）を利用者区分ごとに洗い出し、**想定利用頻度**と**試験への包含**を1本ずつ判定した。凡例: ✅=対象 / −=対象外（理由を右端に記載）。

### 選定の考え方

2つの軸で判定する。

1. **利用頻度:** 高頻度なものほど負荷の主成分になる（閲覧・ログイン等）。
2. **負荷特性:** 頻度が中程度でも、時間集中（受付開始直後に殺到）や整合性リスク（定員・ロック競合）を持つものは重点対象になる。**申込 POST が試験の本命なのはこの軸による**（頻度は「中」だが、集中度と壊れたときの深刻度が全エンドポイント中で最大）。

## 試験1: 申込スパイク試験

### 目的

超人気イベントの受付開始直後に申込が集中したとき、**どこから・どう壊れるか**を特定する。connpass 型サービスで最も危険なパターン。いきなりピーク負荷をかけると「全部壊れた」以上の情報が得られないため、**(a) 限界探索ランプ → (b) スパイク再現**の2部構成とする。

### 事前データ（connpass 級の実態に合わせる）

- ユーザー: 試験用アカウント5,000件（申込者3,000 + 閲覧のみ2,000）を事前シード
- イベント: 対象の超人気イベント1件（定員2,000・キャンセル待ちあり・公開済み）＋背景用イベント5,000件
- **既存データ量も想定規模の時点と同量をシード**: 0の状態の DB で試験すると、データ量が増えて初めて顕在化するボトルネックを見逃す。「数ヶ月後を想定した性能を見る」以上、その時点までに蓄積しているはずのデータ（登録ユーザー約100万行〔connpass 公称ユーザー数相当〕・累計イベント数十万件・申込履歴数百万行）を事前投入する。DB のクエリ性能・インデックス効果は行数に依存するため、空の DB で測ると実態より大幅に良い数字が出てしまう
- セッションは試験開始時に新規作成させる（bcrypt 検証＋セッション INSERT の負荷を含めるため）

### (a) 限界探索ランプ

背景閲覧を混ぜたジャーニー負荷を **5 → 10 → 25 → 50 → 100 RPS** と段階的に引き上げ（各段5分維持）、SLO 違反が最初に発生する負荷帯＝**限界 RPS** と、最初に音を上げるコンポーネント（アプリ CPU / MySQL 接続枯渇 / ロック待ち等）を特定する。

### (b) スパイク再現（合計約17分）

| フェーズ | 時間 | 内容 |
|---|---|---|
| ① ウォームアップ | 3分 | 閲覧ジャーニー 3〜5 RPS（日常ピーク帯）。ベースライン計測 |
| ② 殺到 | 1分 | 1,500人が一斉にログイン→詳細→申込POST。ピーク約 100 RPS |
| ③ 後続 | 10分 | 残り約1,500人の申込＋定員到達後のキャンセル待ち申込＋リロード様子見。約 10〜20 RPS＋背景閲覧 |
| ④ クールダウン | 3分 | 閲覧のみ 3〜5 RPS に戻す。応答時間がベースラインに復帰するか確認 |

※ (a) で限界 RPS が 100 を大きく下回った場合も (b) は実施する。「限界超過の負荷を受けたとき、どう壊れるか（エラーを返して守るのか、整合性まで壊れるのか）と、負荷が去った後に自力回復するか（④）」が (b) の見どころのため。

### 観測項目

**性能面:**

- 各フェーズの p95 応答時間とエラー率（閲覧 GET / 申込 POST を分けて計測）
- MySQL の同時接続数・ロック待ち（`innodb_row_lock_waits`）
- ②→③で劣化したレスポンスが④でベースラインに復帰するか

**整合性面（このアプリ固有の見どころ）:**

- **定員2,000を1人も超過していないこと**（申込トランザクションの排他が高負荷でも守られるか）
- キャンセル待ちの順序が申込順どおりか
- 楽観ロック・重複申込が 500 ではなくユーザー向けエラーで返るか

### 深掘り手順（単体ベンチ）

スパイク試験で SLO 違反が出たエンドポイントのみ、閲覧負荷を外して単体で段階増加させ、そのエンドポイント固有の限界 RPS を特定してレポートに記載する（複合負荷での限界と単体限界の差分が「同居コストがどれだけ足を引っ張っているか」の定量になる）。

## 試験2: ロングランテスト（24時間）

### 目的

短時間の試験では見えない「時間経過で蓄積する劣化」を検出する。メモリリーク、テーブル肥大、キュー滞留、接続リークが対象。

### 負荷パターン

| 要素 | 内容 |
|---|---|
| ベース負荷 | 3〜5 RPS のジャーニー（ログイン→閲覧→申込 or キャンセル）を24時間継続。ログアウトするのは約1割のみで、**残りはセッションを放置**（実利用ではログアウトしない人が多数派のため。放置セッションの蓄積が sessions テーブル観測の前提になる）。複数イベントに分散。低頻度で会員登録・マイページ回遊（参加済み一覧・プロフィール）も混入 |
| 申込サイクル | 「申込→数分後にキャンセル→別ユーザーが申込」を回し続け、キャンセル待ち繰り上げ処理も定常発生させる |
| 小ピーク | 1時間おきに 10 RPS（日常ピークの2〜3倍）× 5分。劣化が進んだ状態でのピーク耐性を毎時観測 |
| 裏処理 | イベント開始時刻を試験期間内に散らして配置し、リマインダー送信ジョブ（キュー）とスケジューラが試験中に自然実行されるようにする |

### 観測項目（1時間ごとのスナップショット）

**プロセス・サーバー側:**

- アプリコンテナのメモリ使用量の推移 — 右肩上がりに増え続けないこと（起動直後の上昇後に水平になるのが正常）
- キューワーカーのメモリ（長時間動く PHP プロセスのためリークの最有力候補）
- DB 接続数の推移（リークすると単調増加する）

**データ蓄積側（構成上の急所）:**

- `sessions` テーブルの行数 — ジャーニーの約9割がログアウトせず放置するため、期限切れ（`SESSION_LIFETIME=120` 分）セッションの掃除が蓄積ペースに追いつくか
- `jobs` / `failed_jobs` の滞留 — リマインダーが処理速度より速く積まれていないか
- `cache` テーブルの肥大
- ログファイル・監査ログの増加ペース（24時間の実測から1年運用時のディスク使用量を外挿）

**性能の経時変化:**

- 毎時の小ピークにおける p95 応答時間を時系列で並べ、1時間目と24時間目で有意に悪化していないこと

### 合否の考え方

「24時間で壊れないか」ではなく「**傾きがゼロに収束するか**」で判断する。メモリ・テーブル行数・応答時間のいずれかが線形増加を続けている場合、その傾きから「何日で限界に達するか」を外挿してレポートに記載する。

## 判断基準（SLO）

- **パーセンタイルは p95 を採用する。** 100パーセンタイル（最悪値）はエッジケース1件に引っ張られて基準として現実的でない。SLA で 99% を求められるアプリもあるが、本アプリの性質では 95% で十分と判断。
- **本来 SLO は要件定義フェーズで定まっているべき値**であり、本試験では仮置きである。実サービス化する際は要件として再定義する。

| 指標 | 閾値 | 適用範囲 |
|---|---|---|
| 閲覧系 GET の p95 | 500ms 以下 | 全フェーズ |
| 申込 POST の p95 | 1,000ms 以下 | スパイク②③含む |
| エラー率（5xx） | 1% 未満 | 全フェーズ（4xx の業務エラーは除外） |
| 定員超過 | 0件 | スパイク試験（1件でも即 NG） |
| メモリの傾き | 24時間で水平収束 | ロングラン |
| 応答時間の経時劣化 | 1時間目比 +20% 以内 | ロングランの毎時ピーク |

### 限界 RPS（本試験の主要成果物）

想定規模では現行構成が SLO を全帯域で満たせない見込みが高いため、SLO は合否判定だけでなく「**どの負荷までなら守れるか**」の物差しとして使う。**全 SLO を満たす最大負荷＝限界 RPS** を限界探索ランプで実測し、通常時トラフィック（平均 約1 RPS／日常ピーク 3〜5 RPS）に対する余裕倍率と、スパイク要求（100 RPS）とのギャップをレポートの中心に据える。

## 「どの機能が危ないか」の判定方法

エンドポイント別に結果を分解し、**リスクマトリクス**で整理する。

- **縦軸:** SLO 違反の深刻度（整合性破壊 ＞ 5xx ＞ 応答遅延）
- **横軸:** そのエンドポイントが受ける負荷の大きさ（スパイク時に集中するか）

右上（深刻度が高く負荷も集中する）に来たものが最優先の改善対象。「攻撃されたら危ないエンドポイント」もこのマトリクスから浮かび上がるため、DDoS 対策の要否はマトリクス確定後に別途判断する。

| 論点 | 決定 |

| 実行環境 | Railway（無料プラン）の本番環境でそのまま実施し、あえて壊れる負荷をかける。弱いサーバーで先に限界を見て原因特定する練習と位置づけ（当初は「想定のみで実行しない」だったが、メンターレビュー 2026-07-12 で実施方針に変更） |

| ロングランの負荷レベル | 3〜5 RPS × 24時間（メンター指定）。換算係数1では日常ピーク帯相当の持続負荷（平均約1 RPSより安全側） |
