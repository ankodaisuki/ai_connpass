# v7 性能試験・ロングランテスト計画（設計）

- **作成日:** 2026-07-11
- **ステータス:** 提案段階（メンターレビュー待ち。承認後に実装計画を作成）
- **目的:** ユーザーが継続的に操作したときにメモリ使用量が異常に増えないか、サーバースペックが足りるか、特定機能がボトルネックにならないかを、実際の使われ方を前提としたシナリオで検証する計画を定める。

## スコープ

### 含むもの

- 画面・API 全ルートの洗い出しと試験対象の選定（「試験対象の選定」の MECE 表を参照）
- 申込スパイク試験（短時間・高負荷）の計画
- 24時間ロングランテスト（定常負荷）の計画
- 負荷モデル（想定規模と RPS の導出根拠）
- 判断基準（SLO）とレポート方法

### 含まないもの（スコープ外）

- **DDoS・悪意ある異常系:** まず通常利用の性能試験を行い、結果のリスクマトリクスから「攻撃されたら危ないエンドポイント」が見えた時点で対策要否を判断する。
- **ツール選定と実装:** 本計画の承認後、次のステップとして実施する。候補は k6 / Locust / Gatling を想定。
- **Google Calendar 実 API への負荷:** 外部サービスのため対象外。含める場合もモック前提。
- **実環境での実行:** 本ドキュメントは想定ベースの計画であり、実行環境の構築・実施は後続フェーズで判断する。

## 前提

- **実行対象の想定:** 本番相当（Railway 単一サービス、MySQL 8.4）
- **アーキテクチャ上の急所:** セッション・キュー・キャッシュがすべて同一 MySQL（`SESSION_DRIVER=database` / `QUEUE_CONNECTION=database` / `CACHE_STORE=database`）。1リクエストあたり複数の DB 書き込みが発生するため、低めの RPS でも DB が中心的なボトルネック候補になる。
- **静的アセット:** カバー画像は R2 配信のため負荷対象外。動的リクエスト（PHP 処理）のみを対象とする。

## シナリオのモデル化方針（採用: ハイブリッド型）

検討した3案から**案C（ハイブリッド）**を採用する。

| 案 | 概要 | 判断 |
|---|---|---|
| A: ユーザージャーニー型 | 仮想ユーザーの一連の行動（ログイン→閲覧→申込→確認）をモデル化 | 主軸として採用 |
| B: エンドポイント単体ベンチ | 個別エンドポイントの限界 RPS を測る | 深掘り手順として補助採用 |
| **C: ハイブリッド（採用）** | A を主軸に、問題が出た箇所だけ B で限界値を特定 | **採用** |

採用理由: セッション・キュー・キャッシュが同一 MySQL に乗る構成では、複合負荷でこそボトルネックが現れる。一方で「どの機能が危ないか」の判定には問題箇所の単体限界値が説得力を持つため、両方を組み合わせる。

## 負荷モデル（規模 → RPS の導出）

### 想定規模（中規模コミュニティ）

| 項目 | 想定値 |
|---|---|
| 登録ユーザー数 | 3,000人 |
| 月間アクティブ | 500人 |
| 同時公開中イベント | 20〜30件 |
| 人気イベントの定員 | 150人（＋キャンセル待ち） |
| 申込殺到の規模 | 受付開始から10分間に300人が申込を試みる（定員の2倍） |

### ジャーニーの定義

1人の申込ジャーニー ＝ ログイン(2リクエスト) → イベント詳細閲覧(2〜3回・リロード含む) → 申込POST(1) → マイページ確認(1) ＝ **約7動的リクエスト/人**。

### RPS の導出

- **スパイクピーク（最初の1分・150人集中）:** 約 **20 RPS**（うち申込 POST 2〜3 RPS、残りは閲覧・認証）
- **スパイク持続（続く10分・残り150人＋キャンセル待ち申込）:** 約 **10 RPS**
- **背景負荷:** 通常閲覧 1〜2 RPS を常時混入
- **ロングラン定常:** **0.5〜2 RPS** を24時間継続 ＋ 1時間おきに 5 RPS × 5分の小ピーク

## 試験対象の選定（画面・API 一覧）

全ルート（41本 = 現行39本 ＋ PR #28 で追加予定の2本）を利用者区分ごとに洗い出し、**想定利用頻度**と**試験への包含**を1本ずつ判定した。凡例: ✅=対象 / −=対象外（理由を右端に記載）。

### 選定の考え方

2つの軸で判定する。

1. **利用頻度:** 高頻度なものほど負荷の主成分になる（閲覧・ログイン等）。
2. **負荷特性:** 頻度が中程度でも、時間集中（受付開始直後に殺到）や整合性リスク（定員・ロック競合）を持つものは重点対象になる。**申込 POST が試験の本命なのはこの軸による**（頻度は「中」だが、集中度と壊れたときの深刻度が全エンドポイント中で最大）。

### 閲覧・認証（未ログイン含む）

| 画面・操作 | ルート | 頻度 | スパイク | ロングラン | 判定理由 |
|---|---|:---:|:---:|:---:|---|
| イベント一覧 | GET / | 高 | ✅ | ✅ | 全ジャーニーの起点。背景負荷の主成分 |
| イベント詳細 | GET /events/{event} | 高 | ✅ | ✅ | 申込前に必ず閲覧。リロード込みで最多アクセス |
| ログイン画面 | GET /login | 高 | ✅ | ✅ | CSRF トークン取得のためジャーニーに必須 |
| ログイン実行 | POST /login | 高 | ✅ | ✅ | bcrypt の CPU 負荷＋セッション作成。スパイク直前に集中 |
| ログアウト | POST /logout | 高 | − | ✅ | ロングランの回遊サイクルに含む。スパイク時は皆滞在し続けるため対象外 |
| 会員登録画面 | GET /register | 低 | − | ✅(低頻度) | users テーブルの成長を24hで観測するため低頻度で混入 |
| 会員登録実行 | POST /register | 低 | − | ✅(低頻度) | 同上（bcrypt ハッシュ生成も発生） |
| 参加者一覧 | GET /events/{event}/attendances | − | − | − | 実体はイベント詳細へのリダイレクトのみ（routes/web.php:36） |

### 参加者の操作

| 画面・操作 | ルート | 頻度 | スパイク | ロングラン | 判定理由 |
|---|---|:---:|:---:|:---:|---|
| **参加申込** | POST /events/{event}/attendances | 中 | ✅ | ✅ | **試験の本命。** 受付開始直後に時間集中し、定員・キャンセル待ちの整合性リスクが最大 |
| 申込キャンセル | DELETE /events/{event}/attendances | 中 | − | ✅ | キャンセル待ち繰り上げ処理を定常発生させる。スパイクは申込側に集中するため対象外 |
| マイ参加予定 | GET /my/attendances | 中 | ✅ | ✅ | 申込直後の確認動線。ジャーニーの終点 |
| 参加済み一覧 | GET /my/attended-events | 中 | − | ✅(低頻度) | 回遊の一部として混入 |
| プロフィール | GET /profile | 中 | − | ✅(低頻度) | 同上 |

### 主催者の操作（すべて対象外）

| 画面・操作 | ルート | 頻度 | スパイク | ロングラン | 判定理由 |
|---|---|:---:|:---:|:---:|---|

| イベント編集（画面/実行） | GET /events/{event}/edit, PUT /events/{event} | 低 | − | − | 同上 |
| イベント削除 | DELETE /events/{event} | 低 | − | − | 低頻度の管理操作 |
| 出欠記録 | PATCH /events/{event}/attendances/{attendance} | 低 | − | − | イベント終了後の主催者操作で集中しない |

### 網羅性の確認

- 上記で全41ルートを重複なく分類済み（MECE）。対象外の行にもすべて理由を付した。
- HTTP ルートに現れない負荷源は2つ: **キューワーカー**（リマインダー送信）と**スケジューラ**。いずれもロングランの裏処理・観測項目としてカバーする。

## 試験1: 申込スパイク試験

### 目的

人気イベントの受付開始直後に申込が集中したとき、性能と整合性が保たれるかを見る。connpass 型サービスで最も危険なパターン。

### 事前データ

- ユーザー: 試験用アカウント500件（申込者300 + 閲覧のみ200）を事前シード
- イベント: 対象の人気イベント1件（定員150・キャンセル待ちあり・公開済み）＋背景用イベント20件
- セッションは試験開始時に新規作成させる（bcrypt 検証＋セッション INSERT の負荷を含めるため）

### シナリオ構成（合計約15分）

| フェーズ | 時間 | 内容 |
|---|---|---|
| ① ウォームアップ | 3分 | 閲覧ジャーニーのみ 1〜2 RPS。ベースライン計測 |
| ② 殺到 | 1分 | 150人が一斉にログイン→詳細→申込POST。ピーク約 20 RPS |
| ③ 後続 | 10分 | 残り150人が分散して申込（定員到達後はキャンセル待ち行き）。約 10 RPS＋背景閲覧 |
| ④ クールダウン | 3分 | 閲覧のみに戻す。応答時間がベースラインに復帰するか確認 |

### 観測項目

**性能面:**

- 各フェーズの p95 応答時間とエラー率（閲覧 GET / 申込 POST を分けて計測）
- MySQL の同時接続数・ロック待ち（`innodb_row_lock_waits`）
- ②→③で劣化したレスポンスが④でベースラインに復帰するか

**整合性面（このアプリ固有の見どころ）:**

- **定員150を1人も超過していないこと**（申込トランザクションの排他が高負荷でも守られるか）
- キャンセル待ちの順序が申込順どおりか
- 楽観ロック・重複申込が 500 ではなくユーザー向けエラーで返るか

### 深掘り手順（単体ベンチ）

スパイク試験で SLO 違反が出たエンドポイントのみ、閲覧負荷を外して単体で 5→10→20 RPS と段階増加させ、「どこから壊れるか」の限界値を特定してレポートに記載する。

## 試験2: ロングランテスト（24時間）

### 目的

短時間の試験では見えない「時間経過で蓄積する劣化」を検出する。メモリリーク、テーブル肥大、キュー滞留、接続リークが対象。

### 負荷パターン

| 要素 | 内容 |
|---|---|
| ベース負荷 | 0.5〜2 RPS のジャーニー（ログイン→閲覧→申込 or キャンセル→ログアウト）を24時間継続。複数イベントに分散。低頻度で会員登録・マイページ回遊（参加済み一覧・プロフィール）も混入 |
| 申込サイクル | 「申込→数分後にキャンセル→別ユーザーが申込」を回し続け、キャンセル待ち繰り上げ処理も定常発生させる |
| 小ピーク | 1時間おきに 5 RPS × 5分。劣化が進んだ状態でのスパイク耐性を毎時観測 |
| 裏処理 | イベント開始時刻を試験期間内に散らして配置し、リマインダー送信ジョブ（キュー）とスケジューラが試験中に自然実行されるようにする |

### 観測項目（1時間ごとのスナップショット）

**プロセス・サーバー側:**

- アプリコンテナのメモリ使用量の推移 — 右肩上がりに増え続けないこと（起動直後の上昇後に水平になるのが正常）
- キューワーカーのメモリ（長時間動く PHP プロセスのためリークの最有力候補）
- DB 接続数の推移（リークすると単調増加する）

**データ蓄積側（構成上の急所）:**

- `sessions` テーブルの行数 — 期限切れセッションが掃除されず肥大しないか
- `jobs` / `failed_jobs` の滞留 — リマインダーが処理速度より速く積まれていないか
- `cache` テーブルの肥大
- ログファイル・監査ログの増加ペース（24時間の実測から1年運用時のディスク使用量を外挿）

**性能の経時変化:**

- 毎時の小ピークにおける p95 応答時間を時系列で並べ、1時間目と24時間目で有意に悪化していないこと

### 合否の考え方

「24時間で壊れないか」ではなく「**傾きがゼロに収束するか**」で判断する。メモリ・テーブル行数・応答時間のいずれかが線形増加を続けている場合、その傾きから「何日で限界に達するか」を外挿してレポートに記載する。

## 判断基準（SLO）

| 指標 | 閾値 | 適用範囲 |
|---|---|---|
| 閲覧系 GET の p95 | 500ms 以下 | 全フェーズ |
| 申込 POST の p95 | 1,000ms 以下 | スパイク②③含む |
| エラー率（5xx） | 1% 未満 | 全フェーズ（4xx の業務エラーは除外） |
| 定員超過 | 0件 | スパイク試験（1件でも即 NG） |
| メモリの傾き | 24時間で水平収束 | ロングラン |
| 応答時間の経時劣化 | 1時間目比 +20% 以内 | ロングランの毎時ピーク |

## 「どの機能が危ないか」の判定方法

エンドポイント別に結果を分解し、**リスクマトリクス**で整理する。

- **縦軸:** SLO 違反の深刻度（整合性破壊 ＞ 5xx ＞ 応答遅延）
- **横軸:** そのエンドポイントが受ける負荷の大きさ（スパイク時に集中するか）

右上（深刻度が高く負荷も集中する）に来たものが最優先の改善対象。「攻撃されたら危ないエンドポイント」もこのマトリクスから浮かび上がるため、DDoS 対策の要否はマトリクス確定後に別途判断する。
