# v7 性能試験・ロングランテスト計画（設計）

- **作成日:** 2026-07-11
- **ステータス:** 提案段階（メンターレビュー待ち。承認後に実装計画を作成）
- **目的:** ユーザーが継続的に操作したときにメモリ使用量が異常に増えないか、サーバースペックが足りるか、特定機能がボトルネックにならないかを、実際の使われ方を前提としたシナリオで検証する計画を定める。

## スコープ

### 含むもの

- 画面・API 全ルートの洗い出しと試験対象の選定（「試験対象の選定」の MECE 表を参照）
- 申込スパイク試験（短時間・高負荷）の計画
- 24時間ロングランテスト（定常負荷）の計画
- 負荷モデル（想定規模と RPS の導出根拠）
- 判断基準（SLO）とレポート方法

### 含まないもの（スコープ外）

- **DDoS・悪意ある異常系:** まず通常利用の性能試験を行い、結果のリスクマトリクスから「攻撃されたら危ないエンドポイント」が見えた時点で対策要否を判断する。
- **ツール選定と実装:** 本計画の承認後、次のステップとして実施する。候補は k6 / Locust / Gatling を想定。
- **Google Calendar 実 API への負荷:** 外部サービスのため対象外。含める場合もモック前提。
- **実環境での実行:** 本ドキュメントは想定ベースの計画であり、実行環境の構築・実施は後続フェーズで判断する。

## 前提

- **実行対象の想定:** 本番相当（Railway 単一サービス、MySQL 8.4）。この構成が想定規模（connpass 級）に耐えない見込みが高いことは織り込み済みで、限界点の特定とスケール改善の入力を得ることが試験の主目的（「負荷モデル」の節を参照）
- **アーキテクチャ上の急所:** セッション・キュー・キャッシュがすべて同一 MySQL（`SESSION_DRIVER=database` / `QUEUE_CONNECTION=database` / `CACHE_STORE=database`）。1リクエストあたり複数の DB 書き込みが発生するため、低めの RPS でも DB が中心的なボトルネック候補になる。
- **静的アセット:** カバー画像は R2 配信のため負荷対象外。動的リクエスト（PHP 処理）のみを対象とする。

## シナリオのモデル化方針（採用: ハイブリッド型）

検討した3案から**案C（ハイブリッド）**を採用する。

| 案 | 概要 | 判断 |
|---|---|---|
| A: ユーザージャーニー型 | 仮想ユーザーの一連の行動（ログイン→閲覧→申込→確認）をモデル化 | 主軸として採用 |
| B: エンドポイント単体ベンチ | 個別エンドポイントの限界 RPS を測る | 深掘り手順として補助採用 |
| **C: ハイブリッド（採用）** | A を主軸に、問題が出た箇所だけ B で限界値を特定 | **採用** |

採用理由: セッション・キュー・キャッシュが同一 MySQL に乗る構成では、複合負荷でこそボトルネックが現れる。一方で「どの機能が危ないか」の判定には問題箇所の単体限界値が説得力を持つため、両方を組み合わせる。

## 負荷モデル（規模 → RPS の導出）

### 試験規模の方針（なぜ現状の利用実績より大きい規模で試験するか）

個人開発で利用実績がないため、シナリオは仮想で決める前提。その上で**現状規模ではなく数ヶ月後に到達しうる想定規模（connpass 級）で初期構築時点から試験する**。

理由: 初期構築時点はエンジニアの体制・知識が最も厚い。後から急にスケールが必要になった際に、対応できるエンジニアを確保できる保証はなく、仕様伝達のコミュニケーションコストもかかる。潰せるボトルネックは体制が厚いうちに早めに潰しておく。また、小さい規模（無料サーバーで余裕のある負荷）で試験しても何もボトルネックが見つからずに終わり、試験の学びがない。

### 想定規模（connpass 級）

| 項目 | 想定値 | 根拠 |
|---|---|---|
| 登録ユーザー数 | 300万人 | connpass 級（100万〜1,000万人帯）の中位 |
| 月間アクティブ（MAU） | 45万人 | 登録の15% |
| 日次アクティブ（DAU） | 5万人 | MAU の約1/9 |
| 同時公開中イベント | 5,000件 | — |
| 通常時トラフィック | 平均 10 RPS／日常ピーク帯 30 RPS | DAU 5万人 × 15リクエスト/日 ≒ 75万リクエスト/日 ≒ 平均 8.7 RPS。時間帯集中で3倍 |
| 超人気イベント | 定員2,000の大型カンファレンス | — |
| 申込殺到の規模 | 受付開始10分間に2万人が申込を試みる（定員の10倍）。うち最初の1分に1.5万人が集中 | connpass の人気イベントは分単位で満席になる実態を反映 |

### ジャーニーの定義

1人の申込ジャーニー ＝ ログイン(2リクエスト) → イベント詳細閲覧(2〜3回・リロード含む) → 申込POST(1) → マイページ確認(1) ＝ **約7動的リクエスト/人**。

### RPS の導出

- **スパイクピーク（最初の1分・1.5万人集中）:** 1.5万人 × 約4リクエスト/分 ÷ 60秒 ≒ **約1,000 RPS**（**通常平均の100倍**。うち申込 POST 100〜200 RPS、残りは閲覧・認証）
- **スパイク持続（続く10分・残り5,000人＋キャンセル待ち申込＋リロード様子見）:** 約 **150 RPS**
- **背景負荷:** 通常閲覧 30 RPS（日常ピーク帯）を常時混入
- **ロングラン定常:** **10〜30 RPS**（日常の平均〜ピーク帯を時間帯変動込みで再現）を24時間継続 ＋ 1時間おきに 100 RPS × 5分の小ピーク

### この規模設定が試験の目的に与える影響

現行構成（Railway 単一サービス＋セッション/キュー/キャッシュ同居の単一 MySQL）が 1,000 RPS に耐えられないことは、試験前からほぼ確実である。したがってこの試験の問いは「**耐えられるか**」ではなく:

1. **どこから壊れるか** — 何 RPS で・どの機能が・どういう壊れ方（遅延/5xx/整合性破壊）をするかの特定（＝限界 RPS の実測）
2. **スケールさせるには何を変えるべきか** — ボトルネックの序列を明らかにし、改善（Redis 分離、コネクションプール、リードレプリカ、水平スケール等）の優先順位の根拠を得る

## 試験対象の選定（画面・API 一覧）

全ルート（41本 = 現行39本 ＋ PR #28 で追加予定の2本）を利用者区分ごとに洗い出し、**想定利用頻度**と**試験への包含**を1本ずつ判定した。凡例: ✅=対象 / −=対象外（理由を右端に記載）。

### 選定の考え方

2つの軸で判定する。

1. **利用頻度:** 高頻度なものほど負荷の主成分になる（閲覧・ログイン等）。
2. **負荷特性:** 頻度が中程度でも、時間集中（受付開始直後に殺到）や整合性リスク（定員・ロック競合）を持つものは重点対象になる。**申込 POST が試験の本命なのはこの軸による**（頻度は「中」だが、集中度と壊れたときの深刻度が全エンドポイント中で最大）。

### 閲覧・認証（未ログイン含む）

## 試験1: 申込スパイク試験

### 目的

超人気イベントの受付開始直後に申込が集中したとき、**どこから・どう壊れるか**を特定する。connpass 型サービスで最も危険なパターン。いきなりピーク負荷をかけると「全部壊れた」以上の情報が得られないため、**(a) 限界探索ランプ → (b) スパイク再現**の2部構成とする。

### 事前データ（connpass 級の実態に合わせる）

- ユーザー: 試験用アカウント3万件（申込者2万 + 閲覧のみ1万）を事前シード
- イベント: 対象の超人気イベント1件（定員2,000・キャンセル待ちあり・公開済み）＋背景用イベント5,000件
- **既存データ量も本番相当にシード**: 申込履歴・過去イベントを数百万行規模で投入する。DB のクエリ性能・インデックス効果は行数に依存するため、空の DB で測ると実態より大幅に良い数字が出てしまう
- セッションは試験開始時に新規作成させる（bcrypt 検証＋セッション INSERT の負荷を含めるため）

### (a) 限界探索ランプ

背景閲覧を混ぜたジャーニー負荷を **30 → 100 → 300 → 600 → 1,000 RPS** と段階的に引き上げ（各段5分維持）、SLO 違反が最初に発生する負荷帯＝**限界 RPS** と、最初に音を上げるコンポーネント（アプリ CPU / MySQL 接続枯渇 / ロック待ち等）を特定する。

### (b) スパイク再現（合計約17分）

| フェーズ | 時間 | 内容 |
|---|---|---|
| ① ウォームアップ | 3分 | 閲覧ジャーニー 30 RPS（日常ピーク帯）。ベースライン計測 |
| ② 殺到 | 1分 | 1.5万人が一斉にログイン→詳細→申込POST。ピーク約 1,000 RPS |
| ③ 後続 | 10分 | 残り5,000人の申込＋定員到達後のキャンセル待ち申込＋リロード様子見。約 150 RPS＋背景閲覧 |
| ④ クールダウン | 3分 | 閲覧のみ 30 RPS に戻す。応答時間がベースラインに復帰するか確認 |

※ (a) で限界 RPS が 1,000 を大きく下回った場合も (b) は実施する。「限界超過の負荷を受けたとき、どう壊れるか（エラーを返して守るのか、整合性まで壊れるのか）と、負荷が去った後に自力回復するか（④）」が (b) の見どころのため。

### 観測項目

**性能面:**

- 各フェーズの p95 応答時間とエラー率（閲覧 GET / 申込 POST を分けて計測）
- MySQL の同時接続数・ロック待ち（`innodb_row_lock_waits`）
- ②→③で劣化したレスポンスが④でベースラインに復帰するか

**整合性面（このアプリ固有の見どころ）:**

- **定員2,000を1人も超過していないこと**（申込トランザクションの排他が高負荷でも守られるか）
- キャンセル待ちの順序が申込順どおりか
- 楽観ロック・重複申込が 500 ではなくユーザー向けエラーで返るか

### 深掘り手順（単体ベンチ）

スパイク試験で SLO 違反が出たエンドポイントのみ、閲覧負荷を外して単体で段階増加させ、そのエンドポイント固有の限界 RPS を特定してレポートに記載する（複合負荷での限界と単体限界の差分が「同居コストがどれだけ足を引っ張っているか」の定量になる）。

## 試験2: ロングランテスト（24時間）

### 目的

短時間の試験では見えない「時間経過で蓄積する劣化」を検出する。メモリリーク、テーブル肥大、キュー滞留、接続リークが対象。

### 負荷パターン

| 要素 | 内容 |
|---|---|
| ベース負荷 | 10〜30 RPS のジャーニー（ログイン→閲覧→申込 or キャンセル→ログアウト）を24時間継続（日常の平均〜ピーク帯を時間帯変動込みで再現）。複数イベントに分散。低頻度で会員登録・マイページ回遊（参加済み一覧・プロフィール）も混入 |
| 申込サイクル | 「申込→数分後にキャンセル→別ユーザーが申込」を回し続け、キャンセル待ち繰り上げ処理も定常発生させる |
| 小ピーク | 1時間おきに 100 RPS × 5分。劣化が進んだ状態でのスパイク耐性を毎時観測 |
| 裏処理 | イベント開始時刻を試験期間内に散らして配置し、リマインダー送信ジョブ（キュー）とスケジューラが試験中に自然実行されるようにする |

### 観測項目（1時間ごとのスナップショット）

**プロセス・サーバー側:**

- アプリコンテナのメモリ使用量の推移 — 右肩上がりに増え続けないこと（起動直後の上昇後に水平になるのが正常）
- キューワーカーのメモリ（長時間動く PHP プロセスのためリークの最有力候補）
- DB 接続数の推移（リークすると単調増加する）

**データ蓄積側（構成上の急所）:**

- `sessions` テーブルの行数 — 期限切れセッションが掃除されず肥大しないか
- `jobs` / `failed_jobs` の滞留 — リマインダーが処理速度より速く積まれていないか
- `cache` テーブルの肥大
- ログファイル・監査ログの増加ペース（24時間の実測から1年運用時のディスク使用量を外挿）

**性能の経時変化:**

- 毎時の小ピークにおける p95 応答時間を時系列で並べ、1時間目と24時間目で有意に悪化していないこと

### 合否の考え方

「24時間で壊れないか」ではなく「**傾きがゼロに収束するか**」で判断する。メモリ・テーブル行数・応答時間のいずれかが線形増加を続けている場合、その傾きから「何日で限界に達するか」を外挿してレポートに記載する。

## 判断基準（SLO）

| 指標 | 閾値 | 適用範囲 |
|---|---|---|
| 閲覧系 GET の p95 | 500ms 以下 | 全フェーズ |
| 申込 POST の p95 | 1,000ms 以下 | スパイク②③含む |
| エラー率（5xx） | 1% 未満 | 全フェーズ（4xx の業務エラーは除外） |
| 定員超過 | 0件 | スパイク試験（1件でも即 NG） |
| メモリの傾き | 24時間で水平収束 | ロングラン |
| 応答時間の経時劣化 | 1時間目比 +20% 以内 | ロングランの毎時ピーク |

### 限界 RPS（本試験の主要成果物）

想定規模では現行構成が SLO を全帯域で満たせない見込みが高いため、SLO は合否判定だけでなく「**どの負荷までなら守れるか**」の物差しとして使う。**全 SLO を満たす最大負荷＝限界 RPS** を限界探索ランプで実測し、通常時トラフィック（平均 10 RPS／日常ピーク 30 RPS）に対する余裕倍率と、スパイク要求（1,000 RPS）とのギャップをレポートの中心に据える。

## 「どの機能が危ないか」の判定方法

エンドポイント別に結果を分解し、**リスクマトリクス**で整理する。

- **縦軸:** SLO 違反の深刻度（整合性破壊 ＞ 5xx ＞ 応答遅延）
- **横軸:** そのエンドポイントが受ける負荷の大きさ（スパイク時に集中するか）

右上（深刻度が高く負荷も集中する）に来たものが最優先の改善対象。「攻撃されたら危ないエンドポイント」もこのマトリクスから浮かび上がるため、DDoS 対策の要否はマトリクス確定後に別途判断する。
