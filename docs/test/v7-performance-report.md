## 3. 限界 RPS とボトルネックの序列

- **限界 RPS（全SLOを満たす最大負荷）:** **50〜100 RPSの間**。50 RPSまでは応答時間・エラー率ともに健全（p95が420〜498ms、エラー率1%未満）。100 RPSで急激に破綻（p95が中央値260ms前後から10秒超まで悪化、エラー率4.46%）
- **通常ピーク（3〜5 RPS）に対する余裕倍率:** 限界50〜100 RPSに対し、通常ピーク3〜5 RPSは約10〜20倍の余裕（ただしスパイク要求100 RPSに対しては余裕なし、次項参照）
- **スパイク要求（100 RPS）とのギャップ:** スパイク試験の想定負荷（殺到1分・約100 RPS）は、今回のランプ試験で確認した限界点と一致または超過する水準。スパイク試験では実際に破綻する可能性が高い（想定内。「限界を超えた負荷でどう壊れ、どう回復するか」を見るのがスパイク試験の目的）
- **最初に音を上げたコンポーネントと根拠:** 未特定（このランプ試験ではRailwayのCPU/メモリメトリクスとの時系列突き合わせは未実施）。中央値が260ms程度で健全なまま維持され、p95/p99のみ急激に悪化する形は、**リクエストの一部がキューイング待ちで滞留している**パターンと整合的（PHP-FPM/Octaneワーカー数の枯渇、またはDB接続プール枯渇が候補）。スパイク試験・ロングラン試験時にRailwayメトリクス（CPU・DB接続数）と突き合わせて特定する

**重要な発見: 限界超過の負荷を受けても、負荷が去れば完全に回復する。** クールダウンのp95（455ms）はウォームアップのp95（457ms）とほぼ同一で、恒久的な劣化・カスケード障害は確認されなかった。また殺到フェーズ（②）のエラー率は0.00%で、ランプ試験の100RPS帯（エラー率4.46%）と対照的——**リクエストは失敗せず、遅くなっただけ**という壊れ方だった。後続フェーズ（③）で中央値は健全なまま維持されつつp95のみ高止まりしているのは、殺到時にキューイングされたリクエストの残滓が徐々に解消していく過程と考えられる（10分のフェーズ内では完全には解消しきらなかった）。

Applied件数がランプ試験後と同じ500件なのは、k6のVU番号が実行ごとに1から振り直されるため、ランプ試験とスパイク試験で概ね同じテストアカウント群が使われ、既に申込済みのアカウントは重複申込エラーとして正しく弾かれた結果（想定内の挙動）。

### 実施上のトラブルと対応

1回目の実行はツール環境側の背景タスク管理により2時間44分（23%）で強制終了された（Mac自体はスリープしておらず、`caffeinate`のクライアント死亡ログで検出）。`nohup`＋`disown`でシェルセッションから完全にプロセスを切り離す方式に変更し、2回目の実行で12時間を完走した。1回目の部分データは `perf/results/longrun_attempt1_killed_at_2h44m.json` として参考保存。

## 3b. 総合評価（3試験を通して）

- **限界RPSは50〜100 RPSの間**（ランプ試験）
- **限界超過時も完全に回復する**（スパイク試験・クールダウンでベースライン復帰）
- **12時間の通常負荷（3〜5 RPS＋毎時ピーク）では劣化ゼロ**（ロングラン試験・p95完全横ばい）
- **整合性は全試験を通して一貫して維持**（定員超過0件・繰り上げ漏れ0件、perf:verifyを4回実施し全てOK）

結論: 本アプリは**通常運用（3〜5 RPS）に対して極めて大きな余裕**（限界の1/10〜1/20）を持ち、12時間の連続稼働でもメモリリークやテーブル肥大の兆候はない。一方で**スパイク的な瞬間負荷（50〜100 RPS超）には弱く**、これが唯一の明確な弱点。

## 6. 改善提案の優先順位

1. **スパイク耐性の強化**（最優先）: 限界RPS（50〜100 RPS）を引き上げる。中央値は健全なままp95のみ悪化する挙動から、PHP-FPMワーカー数またはDB接続プールの枯渇が疑われる。Railwayのアプリサービス側のワーカープロセス数増加、またはMySQL側の`max_connections`見直しから着手するのが妥当
2. **スケジューラ（cron）の欠如を修正**（重要度: 高、性能とは別軸の欠陥）: `docker/supervisord.conf` に `artisan schedule:run` を毎分実行するプログラムが定義されておらず、`covers:prune-orphans`（孤児画像回収）・`perf:snapshot` を含む**全てのLaravelスケジュールタスクが一度も自動実行されていない**ことが判明した。孤児カバー画像が本番でずっと蓄積し続けている可能性がある。`supervisord.conf`に以下のようなcronプログラムを追加すべき:
   ```ini
   [program:scheduler]
   command=sh -c "while true; do php /var/www/html/artisan schedule:run --verbose --no-interaction; sleep 60; done"
   autostart=true
   autorestart=true
   ```
3. **`remember_token`カラムの追加**（既知バグ、7節参照）: ログイン画面の「ログイン状態を保持する」チェックが本番で500エラーになる

## 7. 実施メモ・既知の注意事項

- k6の終了コード非ゼロは「試験失敗」ではなく「限界超過を観測した」正常な結果であり得る（詳細は perf/README.md「注意事項」参照）
- `remember_token` カラム欠如による「ログイン状態を保持する」500エラーは既知バグ。本試験のスコープ外（k6側は回避済み）だが、性能試験とは別に修正を検討すべき
- spike.js のフル実行で `dropped_iterations` が発生したが、エラー率への影響は軽微（0.06%）だったため`preAllocatedVUs`の再調整は行わなかった
- **`perf:snapshot`の毎時自動実行が機能していなかった**（`docker/supervisord.conf`にcronトリガーが存在しないため）。ロングラン試験のメモリ推移は`railway metrics`の手動ポーリングで代替した。これは`covers:prune-orphans`を含む全スケジュールタスクに共通する既存の欠陥で、本試験のスコープを超えるため別チケットでの対応を推奨（6節に改善提案として記載）
- ロングラン試験は1回目が背景タスク管理により2時間44分で強制終了。`nohup`+`disown`でのプロセス切り離しにより2回目で12時間完走した
